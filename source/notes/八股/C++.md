# C++ 八股

## 一、基础语法

### 关键字辨析

#### `const`、`static`、`volatile`、`mutable` 关键字的作用及使用场景分别是什么？
*   **const**: 表示“只读”。修饰变量时，变量不可被修改；修饰指针时，区分指向的内容不可变还是指针本身不可变；修饰成员函数时，表示该函数不会修改类的任何非`mutable`成员变量，且不能调用非`const`成员函数。常用于接口定义、防止误操作。
*   **static**: 
    *   修饰局部变量：改变生命周期，使其存储在静态存储区，直到程序结束，但作用域仍限于函数内。
    *   修饰全局变量/函数：限制作用域为当前文件（内部链接），避免命名冲突。
    *   修饰类成员：属于类而非对象，所有对象共享同一份实例，可通过类名直接访问。常用于计数器、单例模式。
*   **volatile**: 告诉编译器该变量可能会在程序控制之外被改变（如硬件寄存器、多线程共享变量、信号处理），禁止编译器对该变量进行优化（如缓存到寄存器），每次使用都必须从内存重新读取。
*   **mutable**: 用于修饰类的非静态成员变量。即使对象是`const`的，或者在`const`成员函数中，被`mutable`修饰的成员也可以被修改。常用于缓存（cache）、引用计数、互斥锁（mutex）等不影响对象逻辑状态但需要修改的成员。

#### `extern "C"` 的作用是什么？在C++调用C代码或编写DLL导出函数时如何使用？
*   **作用**: 指示编译器按照C语言的规则（名称修饰规则，Name Mangling）来编译指定的代码块。C++支持函数重载，编译后会生成包含参数类型的复杂符号名，而C语言不支持重载，符号名简单。`extern "C"` 使得C++代码能够正确链接到C语言编译的目标文件或库。
*   **使用**: 
    *   调用C代码：在包含C头文件时使用 `#ifdef __cplusplus extern "C" { #include "c_header.h" } #endif`。
    *   编写DLL导出：在导出函数声明前加 `extern "C" __declspec(dllexport)`，确保导出的符号名不被C++修饰，方便其他语言（如C# via P/Invoke）或C程序调用。

#### `inline` 函数的原理是什么？编译器一定会内联吗？虚函数可以是 `inline` 吗？
*   **原理**: 建议编译器将函数体直接插入到调用处，消除函数调用的开销（压栈、跳转、返回）。类似于宏，但有类型检查和作用域限制。
*   **是否一定**: 不一定。`inline` 只是对编译器的建议。如果函数体过大、包含递归、循环复杂，编译器可能会忽略该建议以节省代码体积（避免代码膨胀）。
*   **虚函数**: 可以是 `inline`。但在通过基类指针/引用调用虚函数时（动态绑定），由于运行时才能确定具体调用哪个函数，通常无法内联。只有当编译器能确定具体调用的对象类型（如通过对象直接调用，或开启了LTO全程序优化）时，虚函数才可能被内联。

#### `explicit` 关键字的作用？为什么构造函数建议使用它？
*   **作用**: 修饰单参数构造函数（或多参数但除第一个外都有默认值），禁止编译器进行隐式类型转换。
*   **原因**: 防止意外的隐式转换导致逻辑错误。例如 `class String { String(int n); }; String s = 10;` 如果没有 `explicit`，这会隐式调用构造函数创建一个长度为10的字符串，这可能不是程序员的本意。加上 `explicit` 后，必须显式调用 `String s(10);`。

#### `sizeof` 和 `strlen` 的区别？`sizeof` 在编译期还是运行期计算？
*   **区别**: 
    *   `sizeof` 是运算符，计算数据类型或变量所占内存字节数（包括结束符`\0`对于数组而言）。
    *   `strlen` 是库函数 (`<cstring>`)，计算字符串的有效长度，遇到 `\0` 停止，不包含 `\0`。
    *   `sizeof` 对数组返回整个数组大小，对指针返回指针大小；`strlen` 只能接收 `char*`。
*   **计算时机**: `sizeof` 通常在**编译期**计算（除了变长数组VLA，但C++标准不支持VLA，C99支持）。`strlen` 在**运行期**计算。

### 指针与引用

#### 指针和引用的本质区别是什么？（内存占用、初始化、可变性）
*   **内存占用**: 指针是一个变量，存储地址，占用内存（32位系统4字节，64位系统8字节）；引用是别名，理论上不占用额外内存（底层实现通常为指针，但语义上无独立空间）。
*   **初始化**: 指针可以不初始化（野指针），可以中途改变指向；引用必须在定义时初始化，且一旦绑定不能更改指向。
*   **可变性**: 指针可以为 `nullptr`；引用不能为空（必须绑定有效对象）。
*   **层级**: 有多级指针（`int**`）。

#### 什么是野指针和悬空指针？如何避免？
*   **野指针**: 未初始化的指针，指向随机内存地址。
*   **悬空指针**: 指针指向的内存已经被释放（`delete` 或对象生命周期结束），但指针本身未被置空。
*   **避免**: 
    *   定义时初始化为 `nullptr`。
    *   释放内存后立即将指针置为 `nullptr`。
    *   使用智能指针（`std::unique_ptr`, `std::shared_ptr`）自动管理生命周期。
    *   遵循RAII原则。

#### `const char* p`、`char* const p`、`const char* const p` 的区别？
*   `const char* p` (或 `char const* p`): 指针指向的内容是常量，指针本身可变。即不能通过 `*p` 修改值，但 `p` 可以指向别处。
*   `char* const p`: 指针本身是常量，指向的内容可变。即 `p` 不能指向别处，但可以通过 `*p` 修改值。
*   `const char* const p`: 指针本身和指向的内容都是常量。既不能改指向，也不能改值。
*   **记忆技巧**: `const` 在 `*` 左边修饰内容，在 `*` 右边修饰指针。

#### 指针数组和数组指针的区别？
*   **指针数组** (`int* arr[10]`): 一个数组，里面存了10个 `int*` 指针。优先级 `[]` > `*`。
*   **数组指针** (`int (*p)[10]`): 一个指针，指向一个包含10个 `int` 的数组。优先级 `()` > `[]`。常用于指向二维数组的行。

#### 函数指针和回调函数的应用场景？
*   **函数指针**: 指向函数的指针，允许将函数作为参数传递或存储。
*   **回调函数**: 将函数指针作为参数传递给另一个函数，后者在特定事件发生时调用该函数。
*   **场景**: 现代C++常用 `std::function` 和 `lambda` 替代原始函数指针。

### 类型转换

#### C++四种类型转换 (`static_cast`, `dynamic_cast`, `const_cast`, `reinterpret_cast`) 的区别和使用场景？
*   `static_cast`: 编译期转换。用于基本类型转换、父子类指针/引用转换（上行安全，下行不安全）、`void*` 互转。效率高，无运行时检查。
*   `dynamic_cast`: 运行期转换。主要用于多态体系下的下行转换（基类转子类）或交叉转换。依赖RTTI，如果转换失败返回 `nullptr` (指针) 或抛异常 (引用)。效率较低。
*   `const_cast`: 移除或添加 `const` 属性。常用于调用遗留API需要去除 `const` 限定。
*   `reinterpret_cast`: 低位重解释。将比特流强行解释为另一种类型（如 `int*` 转 `long*`，指针转整数）。极度危险，平台相关，仅在底层驱动或黑客技术中使用。

#### `dynamic_cast` 的底层原理是什么？运行时开销大吗？需要什么条件才能使用？
*   **原理**: 依赖RTTI (Run-Time Type Information)。编译器为每个含虚函数的类生成类型信息表。转换时，遍历继承树检查目标类型是否匹配。
*   **开销**: 较大。涉及运行时查找和比对，比 `static_cast` 慢得多。
*   **条件**: 基类必须有虚函数（启用RTTI），否则编译报错或行为未定义。

### 其他基础

#### 宏定义 (`#define`) 和 `const` / `enum` / `constexpr` 的区别？
*   **宏**: 预处理阶段文本替换，无类型检查，无作用域，易出错（如 `(a+b)*(a+b)` 展开问题），调试困难。
*   **const/enum/constexpr**: 编译期处理，有类型检查，有作用域，可调试。
    *   `const`: 运行时常量（有时编译期优化），有地址。
    *   `enum`: 整型常量集合，类型安全。
    *   `constexpr`: 强制编译期计算，可用于模板参数、数组长度等。
*   **建议**: 尽量不用宏，用 `constexpr` 替代。

#### 位域 (Bit-field) 是什么？内存对齐规则是怎样的？`#pragma pack` 的作用？
*   **位域**: 结构体成员指定占用的位数，用于节省内存（如标志位打包）。
*   **内存对齐**: 为了提高CPU访问效率，变量地址通常是其大小的整数倍。结构体总大小是最大成员对齐值的整数倍。
*   `#pragma pack(n)`: 设置对齐系数为 `n` 字节。用于减少结构体填充（Padding），节省内存（网络包、文件格式），但可能降低访问速度或导致硬件异常（某些架构不允许非对齐访问）。

#### `union` 和 `struct` 的区别？`union` 的大小如何计算？
*   **区别**: `struct` 成员各自拥有独立内存，总大小为各成员大小之和（加对齐）；`union` 所有成员共享同一块内存，同一时间只能存一个成员的值。
*   **大小**: `union` 的大小等于其**最大成员**的大小（并满足对齐要求）。常用于类型双关（Type Punning）或节省内存。

## 二、面向对象编程 (OOP)

### 三大特性

#### 封装、继承、多态的具体含义及在C++中的体现？
*   **封装**: 隐藏内部实现细节，仅暴露接口。C++通过 `public`, `protected`, `private` 访问控制符体现。
*   **继承**: 复用基类代码，建立类层次关系。C++支持单继承和多继承。
*   **多态**: 同一接口不同实现。
    *   静态多态：函数重载、模板（编译期决定）。
    *   动态多态：虚函数（运行期决定）。

#### 继承的方式（public, protected, private）对成员访问权限的影响？
*   **public 继承**: 基类 `public`->子类 `public`，`protected`->`protected`。最常用，“是一个 (Is-A)”关系。
*   **protected 继承**: 基类 `public`/`protected` -> 子类 `protected`。外部无法访问子类继承来的公有成员。
*   **private 继承**: 基类所有成员在子类中都变为 `private`。通常用于“有一个 (Has-A)”关系的实现（组合的替代），此时多态性丧失（外部无法通过子类指针调用基类虚函数）。

#### 多重继承会带来什么问题（菱形继承）？如何解决（虚继承）？虚继承的内存布局是怎样的？
*   **问题**: 菱形继承（A派生B和C，D继承B和C）导致D中存在两份A的副本，造成数据冗余和二义性。
*   **解决**: 使用**虚继承** (`class B : virtual public A`)。确保D中只保留一份A的实例。
*   **内存布局**: 虚继承引入**虚基类表指针 (vbptr)** 和偏移量。访问虚基类成员需要通过指针查表计算偏移，因此比普通继承稍慢。对象布局中，虚基类子对象通常放在派生类对象的末尾。

### **多态与虚函数**

#### 静态多态（重载、模板）和动态多态（虚函数）的区别？
*   **静态多态**: 编译期绑定。效率高，无运行时开销。基于函数签名或模板参数推导。
*   **动态多态**: 运行期绑定。通过虚函数表实现。有间接调用开销，支持基于对象实际类型的灵活扩展。

#### **虚函数表 (vtable) 和虚函数指针 (vptr) 的原理**：它们存放在哪里？何时生成？何时初始化？
*   **vtable**: 存储类中所有虚函数地址的数组。**存放在代码段（只读数据区）**。每个类一份（若该类有虚函数）。编译时生成。
*   **vptr**: 隐藏在对象内部的指针，指向该对象所属类的 vtable。**存放在对象实例内存中**（通常是首地址）。
*   **初始化**: 在构造函数执行期间初始化。先初始化基类部分（vptr指向基类vtable），再初始化派生类部分（vptr指向派生类vtable）。这也是为什么构造函数中不能发挥多态的原因。

#### 构造函数和析构函数中可以调用虚函数吗？会发生什么？
*   **可以调用**，但**不会发生多态**。
*   **原因**: 构造/析构时，对象的 vptr 指向当前正在构造/析构的类的 vtable，而不是最终派生类的 vtable。
*   **后果**: 调用的是当前类版本的函数，而不是子类的重写版本。若在基类构造函数调用纯虚函数，会导致链接错误或运行时崩溃（因为纯虚函数无实现）。

#### 为什么基类的析构函数必须是虚函数？如果不是会怎样？
*   **原因**: 当通过基类指针删除派生类对象时 (`delete basePtr`)，如果基类析构不是虚函数，编译器只会调用基类的析构函数，**不会调用派生类的析构函数**。
*   **后果**: 派生类中分配的资源（如内存、文件句柄）无法释放，导致**内存泄漏**或资源未释放。
*   **规则**: 只要类中有虚函数，析构函数就应设为虚函数。

#### 纯虚函数和抽象类的定义？抽象类能实例化吗？
*   **纯虚函数**: 声明为 `virtual void func() = 0;` 的函数，无实现（或有实现但不能直接调用）。
*   **抽象类**: 包含至少一个纯虚函数的类。
*   **实例化**: 抽象类**不能**实例化对象。只能作为接口或基类，由派生类实现所有纯虚函数后才能实例化。

#### `override` 和 `final` 关键字的作用？
*   `override`: 标记虚函数意在重写基类虚函数。如果基类没有匹配的虚函数（签名不同或忘记写virtual），编译器报错。增强代码安全性。
*   `final`: 
    *   修饰类：该类不能被继承。
    *   修饰虚函数：该函数不能在派生类中被重写。
    *   用于封闭继承体系，优化（编译器可能去虚拟化）或设计约束。

### 对象生命周期	

#### 构造函数、拷贝构造函数、移动构造函数、赋值运算符、析构函数的调用顺序？
*   **构造**: 基类 -> 成员对象 -> 自身构造函数体。
*   **析构**: 自身析构体 -> 成员对象（逆序） -> 基类（逆序）。
*   **拷贝/移动构造**: 同构造顺序，先初始化基类和成员，再执行函数体。
*   **赋值**: 先检查自赋值，然后通常先销毁原有资源（或直接覆盖），再拷贝/移动新资源。

#### 深拷贝与浅拷贝的区别？何时需要手动实现拷贝控制（Rule of Three/Five）？
*   **浅拷贝**: 默认行为。逐字节复制，对于指针成员，只复制地址，导致两个对象指向同一块堆内存。析构时会重复释放（Double Free）。
*   **深拷贝**: 手动实现。为新对象分配新的内存，并复制指针指向的内容。
*   **Rule of Three (C++98)**: 如果类需要自定义析构函数、拷贝构造函数或拷贝赋值运算符中的任何一个，通常也需要自定义另外两个。
*   **Rule of Five (C++11+)**: 加上移动构造函数和移动赋值运算符。如果类管理资源（如裸指针、文件描述符），通常需要手动实现这五个特殊成员函数，或禁用拷贝/移动，或使用智能指针自动管理。

## 三、内存管理 (Memory Management)

### 内存布局
#### C++程序的内存分区（栈、堆、全局/静态区、常量区、代码区）分别存储什么数据？
*   **栈 (Stack)**: 局部变量、函数参数、返回地址。由编译器自动分配释放，速度快，容量小。
*   **堆 (Heap)**: `new`/`malloc` 分配的动态内存。手动管理，碎片化风险，容量大。
*   **全局/静态区**: 全局变量、`static` 变量。程序启动时分配，结束时释放。
*   **常量区**: 字符串字面量、`const` 变量（有时）。只读。
*   **代码区**: 存放二进制指令、虚函数表等。只读。

### 动态内存分配
#### `new`/`delete` 与 `malloc`/`free` 的本质区别？
*   **语言属性**: `new`/`delete` 是C++运算符；`malloc`/`free` 是C库函数。
*   **构造/析构**: `new` 会调用构造函数，`delete` 会调用析构函数；`malloc`/`free` 仅分配/释放原始内存，不管理对象生命周期。
*   **类型安全**: `new` 返回具体类型指针，无需强转；`malloc` 返回 `void*`。
*   **失败处理**: `new` 失败抛出 `std::bad_alloc` (除非用 `nothrow`)；`malloc` 失败返回 `NULL`。
*   **大小计算**: `new` 自动计算类型大小；`malloc` 需手动传入字节数。

#### `new` 操作的底层流程？
1.  调用 `operator new(size_t)` 分配原始内存（类似 malloc）。
2.  在分配的内存上调用**构造函数**初始化对象。
3.  返回对象指针。
*   _placement new_ 允许在已分配的内存上构造对象。

#### 内存泄漏 (Memory Leak) 的常见原因及检测工具？
*   **原因**: `new` 后忘记 `delete`；异常导致跳过 `delete`；循环引用（`shared_ptr`）；全局容器只增不减。
*   **工具**: 
    *   Windows: Visual Studio Diagnostic Tools, CRT Debug Heap (`_CrtDumpMemoryLeaks`).
    *   Linux/Mac: Valgrind (Memcheck), AddressSanitizer (ASan).
    *   游戏引擎自带 Profiler (Unity Profiler, Unreal Insights).

### 智能指针 (Smart Pointers)
#### `std::shared_ptr`、`std::unique_ptr`、`std::weak_ptr` 的原理和区别？
*   `unique_ptr`: 独占所有权，不可拷贝，只能移动。轻量级，零开销（相比裸指针）。析构时自动删除对象。
*   `shared_ptr`: 共享所有权，内部维护**引用计数**。拷贝时计数+1，析构时-1，归零时删除对象。线程安全（计数操作原子，但对象访问非线程安全）。
*   `weak_ptr`: 弱引用，不增加引用计数。配合 `shared_ptr` 解决循环引用问题。需通过 `lock()` 提升为 `shared_ptr` 才能访问对象。

#### `shared_ptr` 的引用计数是如何实现的？线程安全吗？
*   **实现**: 控制块 (Control Block) 中存储引用计数（强引用和弱引用）。
*   **线程安全**: 引用计数的增减是**原子操作**，线程安全。但是，**多个线程同时读写同一个 `shared_ptr` 管理的对象本身**是不安全的，需要额外加锁。多个线程操作不同的 `shared_ptr` 实例（即使指向同一对象）是安全的。

#### `shared_ptr` 的循环引用问题如何解决？
*   **问题**: A持有B的 `shared_ptr`，B持有A的 `shared_ptr`，导致计数永不为0，内存泄漏。
*   **解决**: 将其中一方的 `shared_ptr` 改为 `weak_ptr`。打破强引用环。

#### `make_shared` 和 `new` 创建 `shared_ptr` 的区别？
*   `new`: 两次内存分配（一次给对象，一次给控制块）。
*   `make_shared`: **一次内存分配**，将对象和控制块放在一起。性能更好，缓存更友好。
*   **注意**: `make_shared` 创建的对象，其内存只有在最后一个 `weak_ptr` 也销毁后才会释放（因为控制块和对象在一起），可能导致大对象内存无法及时归还。

### RAII 机制
#### RAII (Resource Acquisition Is Initialization) 的核心思想是什么？
*   **思想**: 利用栈对象的生命周期自动管理资源。在构造函数中获取资源（内存、锁、文件），在析构函数中释放资源。
*   **优势**: 保证异常安全，无论函数正常返回还是抛出异常，局部对象析构都会执行，资源必被释放。是C++资源管理的基石（如 `std::lock_guard`, `std::fstream`, 智能指针）。

## 四、泛型编程 (Generic Programming / Templates)

### 模板基础
#### 函数模板和类模板的区别？
*   **函数模板**: 编译器根据实参类型自动推导模板参数（如 `std::max(a, b)`）。
*   **类模板**: 编译器通常**不能**自动推导模板参数（C++17之前），必须显式指定（如 `std::vector<int>`）。C++17引入了类模板参数推导 (CTAD)。

#### 模板特化 (Specialization) 和偏特化 (Partial Specialization) 的区别及应用？
*   **全特化**: 指定所有模板参数的具体类型。如 `template<> class MyVector<bool> { ... };`。
*   **偏特化**: 只指定部分参数，或对参数施加约束（如指针、数组）。如 `template<typename T> class MyVector<T*> { ... };`。
*   **应用**: 针对特定类型（如 `bool`, 指针）进行性能优化或特殊逻辑处理。函数模板不支持偏特化，只能通过重载实现。

### 高级特性
#### 变长模板参数 (Variadic Templates) 的原理及应用？
*   **原理**: 允许模板接受任意数量的参数 (`template<typename... Args>`)。通过递归展开或折叠表达式 (C++17) 处理。
*   **应用**: `std::tuple`, `std::bind`, `std::thread` 构造函数，日志打印函数，完美转发工厂函数。

#### SFINAE (Substitution Failure Is Not An Error) 原则是什么？`std::enable_if` 的作用？
*   **SFINAE**: 在模板实例化过程中，如果替换模板参数导致非法代码，该特化会被简单地从重载集中移除，而不是报错。
*   **`std::enable_if`**: 利用SFINAE，根据条件（如类型特征 `std::is_integral`）启用或禁用某个函数模板。常用于约束模板参数类型。

#### `decltype` 和 `auto` 的推导规则？
*   `auto`: 根据初始化表达式推导类型，忽略引用和顶层const（除非显式加 `&` 或 `const`）。
*   `decltype`: 严格推导表达式的类型，保留引用和const。`decltype(x)` 若x是变量则带引用；`decltype((x))` 强制带引用。

#### 右值引用、左值引用、万能引用的区别？
*   **左值引用 (`T&`)**: 绑定左值。
*   **右值引用 (`T&&`)**: 绑定右值（临时对象），用于移动语义。
*   **万能引用 (Forwarding Reference, `T&&` in template)**: 在模板中 `T&&`，根据实参是左值还是右值，分别推导为 `T&` 或 `T&&`。用于完美转发。

#### 移动语义和完美转发的原理及性能优势？
*   **移动语义**: 通过转移资源所有权（如指针接管）代替深拷贝，大幅减少内存分配和复制开销。核心是移动构造函数和 `std::move`。
*   **完美转发**: 在泛型代码中，保持实参的左值/右值属性和const属性，原封不动地传递给其他函数。核心是 `std::forward`。
*   **优势**: 消除不必要的临时对象拷贝，提升性能，尤其在容器扩容、字符串拼接、函数包装器中。

#### `std::move` 的本质是什么？
*   **本质**: 一个强制类型转换，将左值转换为右值引用 (`static_cast<T&&>(x)`)。
*   **注意**: 它**不移动**任何东西，只是标记该对象“可以被移动”。真正的移动发生在后续调用的移动构造函数或移动赋值运算符中。使用后原对象处于有效但未定义状态（不应再使用，除非重新赋值）。

## 五、异常处理 (Exception Handling)

### 机制原理
#### C++ 异常处理的底层实现机制？
*   **模型**: 通常采用**零开销抽象**（Zero-cost abstraction，如GCC的DW2/Itanium模型）。正常执行路径无额外指令，异常发生时通过查找预先生成的异常表（.eh_frame）来确定栈展开方式和catch块位置。
*   **对比**: 旧式模型（如MSVC的部分模式）可能在每个调用点插入检查代码，有运行时开销。

#### `try-catch-throw` 的执行流程？栈展开 (Stack Unwinding) 过程发生了什么？
*   **流程**: `throw` 创建异常对象 -> 寻找匹配的 `catch` -> 若找到，执行 `catch` 块；若未找到，调用 `std::terminate`。
*   **栈展开**: 从抛出点向上回溯栈帧，**销毁**沿途所有已构造的局部对象（调用析构函数），直到到达处理该异常的 `catch` 块。这是RAII生效的关键时刻。

#### 异常对象是传值还是传引用？
*   `throw` 时：异常对象通常会被**拷贝**（或移动）到特殊内存区域（异常存储区）。
*   `catch` 时：
    *   `catch(T e)`: 再次拷贝。
    *   `catch(T& e)`: 引用，无拷贝，推荐方式（避免切片和拷贝开销）。
    *   `catch(const T& e)`: 最佳实践。

### 规范与实践
#### 构造函数中抛出异常要注意什么？
*   **风险**: 对象未构造完成，析构函数不会被调用。若构造函数中已经分配了部分资源（裸指针），这些资源会泄漏。
*   **对策**: 在构造函数中使用 RAII（如智能指针、`std::vector`）管理资源，确保异常发生时自动清理。避免在构造函数体中做复杂逻辑，尽量在初始化列表中完成。

#### 析构函数中可以抛出异常吗？
*   **禁止**: 绝不要在析构函数中抛出异常。
*   **原因**: 如果析构函数在处理栈展开（因其他异常）时被调用，此时若再抛出异常，会导致两个活跃异常，程序直接调用 `std::terminate` 崩溃。
*   **做法**: C++11起析构函数默认 `noexcept(true)`。若有潜在异常操作，需在析构函数内部 `try-catch` 吞掉或记录日志。

#### `noexcept` 关键字的作用？
*   **作用**: 声明函数不会抛出异常。
*   **好处**: 
    1.  编译器优化（移除异常处理代码路径）。
    2.  `std::vector` 等容器在扩容时，若元素移动构造函数是 `noexcept`，会使用移动而非拷贝（保证强异常安全）。
    3.  若标记为 `noexcept` 的函数实际抛出了异常，直接调用 `std::terminate`。

#### 异常与性能的关系？游戏主循环中是否推荐使用异常？
*   **性能**: 抛出异常开销极大（栈展开、查找表）。
*   **游戏开发**: **不推荐**在游戏主循环（Game Loop）、高频渲染或物理更新中使用异常控制流程。异常应仅用于“真正异常”的情况（如资源加载失败、严重逻辑错误）。对于预期内的错误（如找不到物体），应使用错误码、`std::optional` 或返回布尔值处理。

## 六、标准库 (STL & Standard Library)

### 容器 (Containers)
#### `vector`、`list`、`deque` 的底层数据结构、内存布局及扩容机制？
*   `vector`: 
    *   **结构**: 动态数组，连续内存。
    *   **扩容**: 容量不足时，分配新内存（通常1.5倍或2倍），拷贝/移动旧元素，释放旧内存。
    *   **特点**: 随机访问O(1)，尾部插入O(1)（均摊），中间插入/删除O(n)。扩容代价大，可用 `reserve` 预分配。
*   `list`: 
    *   **结构**: 双向链表，节点分散在堆上。
    *   **特点**: 任意位置插入/删除O(1)（已知迭代器），不支持随机访问。内存不连续，缓存不友好。
*   `deque`: 
    *   **结构**: 分段连续（中控地图 + 多个固定大小缓冲区）。
    *   **特点**: 首尾插入/删除O(1)，支持随机访问（稍慢于vector）。

#### `map`、`set` 与 `unordered_map`、`unordered_set` 的区别？
*   `map`/`set`: 
    *   **底层**: **红黑树**（自平衡二叉搜索树）。
    *   **特性**: 有序，查找/插入/删除 O(log N)。
*   `unordered_map`/`unordered_set`: 
    *   **底层**: **哈希表**（数组+链表/红黑树）。
    *   **特性**: 无序，查找/插入/删除 平均 O(1)，最坏 O(N)。需要自定义哈希函数。

#### 迭代器失效的规则总结？
*   `vector`: 插入/删除（除尾部插入且未扩容）导致所有迭代器失效；扩容导致所有迭代器失效。
*   `list`/`map`/`set`: 仅被删除元素的迭代器失效，其他不受影响。
*   `deque`: 头部插入/删除使所有迭代器失效；尾部插入可能使所有失效；中间删除使该点及之后失效。
*   **通用**: 容器重组（rehash, resize）通常导致失效。

### 算法与函数对象
#### 仿函数 (Functor) 与函数指针、Lambda 表达式的区别？
*   **函数指针**: 轻量，但不能携带状态（上下文）。
*   **仿函数**: 类对象，重载 `operator()`，可以携带成员变量作为状态。编译器易于内联优化。
*   **Lambda**: 匿名仿函数，语法简洁，可捕获局部变量。本质是生成了一个闭包类。

#### Lambda 表达式的捕获列表 (`[=]`, `[&]`, `[this]`) 的含义及陷阱？
*   `[=]`: 值捕获所有外部变量（副本）。
*   `[&]`: 引用捕获所有外部变量。
*   `[this]`: 捕获当前对象指针。
*   **陷阱**: 
    *   **悬空引用**: 按引用捕获局部变量，若Lambda生命周期长于变量，导致崩溃。
    *   **异步执行**: 在多线程中按引用捕获栈变量极其危险。
    *   **循环引用**: Lambda捕获 `shared_ptr` 指向自身所在对象，导致引用计数无法归零。

### 其他组件
#### `std::string` 的实现原理（SSO - Small String Optimization）？
*   **SSO**: 对于短字符串（通常15-22字节，取决于实现），直接在 `string` 对象内部的缓冲区存储字符，避免堆分配。
*   **优势**: 减少内存分配次数，提升小字符串性能，减少碎片。
*   **结构**: 联合体或变体，区分是内部缓冲还是堆指针。

## 七、并发与多线程 (Concurrency)

### 基础概念
#### 进程与线程的区别？
*   **进程**: 资源分配的最小单位，拥有独立内存空间，切换开销大。
*   **线程**: CPU调度的最小单位，共享进程内存（堆、全局区），拥有独立栈，切换开销小。

#### 竞态条件 (Race Condition) 和数据竞争 (Data Race)？
*   **竞态条件**: 程序行为依赖于线程执行的相对时序，导致结果不确定（逻辑错误）。
*   **数据竞争**: 两个以上线程同时访问同一内存位置，且至少有一个是写操作，且无同步机制。这是C++标准定义的未定义行为 (UB)。

### 同步机制
#### `std::mutex`、`std::recursive_mutex` 的区别？
*   `mutex`: 不可重入。同一线程重复加锁会死锁。
*   `recursive_mutex`: 可重入。同一线程可多次加锁，需对应次数解锁。开销稍大，尽量避免使用，通常意味着设计需重构。

#### 互斥锁的死锁产生条件及预防？
*   **条件**: 互斥、占有并等待、不可抢占、循环等待。
*   **预防**: 
    *   固定锁获取顺序。
    *   使用 `std::lock` 或 `std::scoped_lock` 一次性获取多个锁。
    *   尝试锁 (`try_lock`) 超时放弃。
    *   减少锁粒度，缩短持锁时间。

#### 条件变量 (`std::condition_variable`) 为什么要用 `while` 循环检查条件？
*   **原因**: 
    1.  **虚假唤醒 (Spurious Wakeup)**: 操作系统可能无理由唤醒线程。
    2.  **竞争**: 唤醒后，其他线程可能先抢占了锁并改变了条件。
*   **做法**: `while(!condition) cv.wait(lock);` 确保醒来时条件确实满足。

#### 原子操作 (`std::atomic`) 与内存序 (Memory Order)？
*   **原子**: 保证操作不可分割，无数据竞争。
*   **内存序**: 控制指令重排序。
    *   `memory_order_relaxed`: 仅保证原子性，无同步顺序。
    *   `memory_order_acquire` / `release`: 配对使用，实现同步（如生产者-消费者）。
    *   `memory_order_seq_cst`: 默认，最强一致性，全局顺序一致，开销最大。

### 现代C++并发
#### `std::future`、`std::promise` 的作用？
*   用于异步任务的结果传递。`promise` 设置值，`future` 获取值（可阻塞等待）。实现线程间的一次性数据同步。

#### 线程池 (Thread Pool) 的设计思路？
*   **目的**: 避免频繁创建/销毁线程的开销，控制并发数量。
*   **组成**: 
    *   一组工作线程（阻塞在任务队列上）。
    *   任务队列（线程安全的 `std::queue<std::function<void()>>`）。
    *   同步机制（mutex + condition_variable）。
    *   提交接口 (`submit`) 和关闭机制。

## 八、游戏开发特定场景 (Game Dev Specifics)

### 性能优化
#### 什么是缓存友好性 (Cache Friendliness)？SOA 与 AOS 的区别？
*   **缓存友好**: 数据布局符合CPU缓存行（Cache Line，通常64字节）的加载机制，减少 Cache Miss。
*   **AOS (Array of Structures)**: `struct Player { x, y, z; health; }; Player arr[N];`。访问 `health` 时会加载整个结构体到缓存，若只关心 `health` 则浪费带宽。
*   **SOA (Structure of Arrays)**: `struct Players { float x[N], y[N], z[N], health[N]; };`。访问 `health` 时只加载相关数据，适合批量处理（ECS架构核心思想），SIMD优化友好。

#### 如何减少动态内存分配（内存池 Memory Pool 的设计）？
*   **问题**: `new/delete` 频繁调用导致堆碎片和系统调用开销，引起帧率抖动（Stuttering）。
*   **内存池**: 预先分配一大块内存，将其切分为固定大小的块。分配时从空闲链表取一块，释放时归还链表。
*   **应用**: 游戏中的子弹、特效粒子、网络包等高频生灭对象。

#### 虚函数调用的性能开销有多大？在什么情况下应避免使用？
*   **开销**: 一次间接寻址（查vtable）+ 无法内联（通常）。在现代CPU上约几纳秒，但在每帧百万次调用的循环中累积显著。
*   **避免场景**: 
    *   超高频循环（如粒子更新、大规模实体遍历）。
    *   热路径代码。
    *   **替代方案**: 使用模板（CRTP静态多态）、函数指针表、或数据驱动的状态机。

### 与其他语言交互 (Unity相关)
#### C++ 与 C# 交互的基本原理（P/Invoke, CppPlugin）？
*   **原理**: Unity (Mono/IL2CPP) 通过 P/Invoke (Platform Invoke) 调用 C++ 导出的 C 风格函数 (`extern "C"`)。
*   ** marshaling**: 需要处理数据类型映射（如 `string` <-> `char*`, `Vector3` <-> `struct`）。
*   **调用开销**: 存在跨运行时边界开销（Marshaling, 上下文切换），不宜在极高频循环（如每帧每物体）中频繁调用。应将逻辑批处理或在C++侧完成循环。

#### 数据类型在 C++ 和 C# 之间的映射关系？
*   `int` <-> `int`, `float` <-> `float`, `double` <-> `double`.
*   `char*` (UTF-8) <-> `string` (需注意编码和内存所有权).
*   `struct` (POD) <-> `struct` (LayoutKind.Sequential).
*   数组: 需传递指针和长度，或使用 `GCHandle` 固定内存。

#### 垃圾回收 (GC) 对C++托管代码的影响？
*   **场景**: 在C++插件中创建C#对象（通过反射或回调），或C#传递委托给C++。
*   **影响**: C++持有的C#对象引用若未被GC根（Root）标记，可能被回收，导致悬空指针。
*   **对策**: 使用 `GCHandle.Alloc(obj, GCHandleType.Normal)` 在C#侧固定对象，或在C++侧维护引用计数并通知C#侧保持存活。在IL2CPP模式下，GC行为有所不同，需注意AOT编译限制。
