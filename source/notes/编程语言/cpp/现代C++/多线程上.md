# 线程基础

C++11 首次在标准库中引入了 `<thread>` 头文件，提供了跨平台的线程操作接口，结束了 C++ 依赖操作系统 API（如 Windows 的`CreateThread`、Linux 的`pthread`）实现多线程的历史。核心特性包括**线程创建**、**线程管理**、**线程标识**等，是现代 C++ 并发编程的基础。

## 背景

C++11 前实现多线程的问题：

1. **平台依赖**：Windows 用`Win32 API`，Linux 用`pthread`，代码无法跨平台；
2. **语法繁琐**：需手动管理线程句柄、错误码，代码冗余；
3. **类型不安全**：函数指针传递易出错，缺乏类型检查。

## 核心概念与基础语法

### 线程创建

`std::thread` 是 C++11 表示线程的核心类，创建时传入**可调用对象**（函数、Lambda、函数对象、`std::function`）即可启动线程。

**关键规则**

- **线程启动**：`std::thread` 对象创建时，子线程立即启动执行可调用对象；
- **线程等待**：必须调用 `join()`（等待子线程结束）或 `detach()`（分离线程），否则主线程结束时会调用`std::terminate`终止程序；
- **参数传递**：默认按值传递，若需传引用，需用`std::ref`/`std::cref`包装；
- **不可拷贝**：`std::thread` 不支持拷贝（拷贝构造 / 赋值被删除），仅支持移动（`std::move`）。

```c++
// 普通函数：线程执行体
void thread_func(int num, const string& msg) {
    cout << "子线程：num=" << num << ", msg=" << msg << endl;
}
// 1. 创建线程：传入可调用对象+参数
thread t(thread_func, 10, "hello thread");
// 2. 等待线程结束（必须！否则主线程退出会终止子线程）
t.join();
```

**核心成员函数**

| 成员函数                          | 功能                                                         |
| --------------------------------- | ------------------------------------------------------------ |
| `join()`                          | 阻塞当前线程，等待子线程执行完毕（主线程等子线程）           |
| `detach()`                        | 分离线程：子线程后台运行，与主线程无关联，由系统回收资源（无法再 join） |
| `joinable()`                      | 判断线程是否可 join/detach（未 join、未 detach、未移动则返回 true） |
| `get_id()`                        | 返回线程 ID（类型`std::thread::id`），用于标识线程           |
| `swap()`                          | 交换两个`std::thread`对象的线程资源                          |
| `native_handle()`                 | 返回当前线程对象对应的**底层系统原生线程句柄**，类型由平台决定 |
| `std::this_thread::get_id()`      | 获取当前线程的 ID                                            |
| `std::this_thread::sleep_for()`   | 当前线程休眠指定时长（如`sleep_for(1s)`）                    |
| `std::this_thread::yield()`       | 当前线程主动让出 CPU，让其他线程执行                         |
| `std::this_thread::sleep_until()` | 让当前线程休眠，直到指定的绝对时间点到达为止                 |

### 线程参数传递

`std::thread` 构造时：

1. **默认会对所有参数进行【拷贝 / 移动】**，不会直接传递引用！
2. 线程内部拿到的是**副本**，不是原变量！
3. 想传**引用**必须用 `std::ref` / `std::cref` 包装！
4. 传指针、动态内存要注意**生命周期**（主线程别提前销毁）

**值传递（最安全、最常用）**

直接传普通变量，线程内部是**拷贝**，互不影响。

```c++
void func(int x) {
    x = 100;  // 修改的是副本
}
int a = 10;
thread t(func, a);  // 值传递 → 拷贝
```

- **优点**：安全，无生命周期问题
- **缺点**：无法修改原变量，大对象拷贝有开销

**引用传递（`std::ref`）**

不加 ref 会编译失败 / 出错，`thread` 默认不允许隐式引用传递。直接传&是**传递指针值**

```c++
void func(int &x) {
    x = 100;  // 修改原变量
}
int a = 10;
thread t(func, ref(a)); // 必须用 std::ref 包装！
```

- **用途**：线程修改外部变量、减少拷贝开销
- **危险**：必须保证变量在线程运行期间**不被销毁**

**const 引用传递（`std::cref`）**

只读场景使用，防止意外修改：

```c++
void func(const int &x) {}
thread t(func, cref(a));
```

**指针传递**

直接传地址，**效率最高，但最危险**。如果主线程先退出 / 变量先销毁，子线程访问野指针，则**程序崩溃**

```c++
void func(int *p) {
    *p = 100;
}
int a = 10;
thread t(func, &a);
```

**类成员函数做线程函数**

**必须传递 `this` 指针**

```c++
class Test {
public:
    int num = 10;
    void func(int x) {
        num = x;
    }
};
Test obj;
thread t(&Test::func, &obj, 100);// 语法：线程对象，成员函数地址，对象地址，参数
```

**Lambda 表达式传参**

Lambda 可以直接**值捕获、引用捕获**

```c++
int a = 10;
thread t([&]() {
    a = 100;
});
```

# 互斥与锁

`<mutex>` 头文件中提供了标准化的**互斥锁（Mutex）** 和**锁管理工具**，核心用于解决多线程共享数据的**数据竞争（Data Race）** 问题，保证临界区（Critical Section）代码的原子性执行。这结束了 C++ 依赖平台特定锁 API（如 Linux 的`pthread_mutex`、Windows 的`CRITICAL_SECTION`）的历史，实现了跨平台的线程同步。

## 背景

数据竞争：多线程同时读写共享数据时，会因 CPU 调度的随机性导致数据状态错乱（数据竞争）

互斥锁的核心作用是**互斥访问**：同一时间仅允许一个线程进入临界区，保证共享数据操作的原子性。

## 基础通用特性

1. **独占性**：互斥锁保证同一时间仅有一个线程可获取独占所有权；
2. **线程所有权**：仅持有锁的线程可执行解锁操作，否则触发未定义行为；
3. **不可拷贝 / 移动**：所有标准互斥锁均不支持拷贝构造、拷贝赋值，仅可移动；
4. **RAII 安全**：推荐搭配锁管理工具使用，避免手动加锁 / 解锁导致的死锁、资源泄漏。

## 核心互斥锁类型

| 互斥锁类型                   | 互斥锁名称             | 核心特性                               | 适用场景                           |
| ---------------------------- | ---------------------- | -------------------------------------- | ---------------------------------- |
| `std::mutex`                 | 基础互斥锁             | 非递归、不可超时                       | 绝大多数普通同步场景               |
| `std::recursive_mutex`       | 递归互斥锁             | 允许同一线程多次加锁（需对应次数解锁） | 递归函数中的同步、同一线程多次加锁 |
| `std::timed_mutex`           | 带超时的互斥锁         | 超时返回失败                           | 需避免死锁、支持超时等待的场景     |
| `std::recursive_timed_mutex` | 带超时的递归互斥锁     | 允许同一线程多次加锁，超时返回失败     | 递归函数 + 超时等待的场景          |
| `std::shared_mutex`          | 读写共享互斥锁         | 支持**共享读 / 独占写**，C++17         | 读多写少、高并发读取场景           |
| `std::shared_timed_mutex`    | 带超时的读写共享互斥锁 | 支持共享 / 独占 + 超时，C++14          | 读写分离 + 超时等待的高级场景      |

### 基础互斥锁：`std::mutex`

**定义**：C++11 标准提供的基础独占互斥锁，是线程同步的核心基础组件。

**核心特性**

- 非递归：同一线程不可重复加锁，重复加锁会导致死锁；
- 无超时机制：`lock()` 会无限阻塞直至获取锁；
- 独占访问：同一时间仅一个线程持有锁。

**适用场景**：无嵌套调用、无超时需求的**通用临界区保护**，是最常用的基础互斥锁。

| 函数         | 功能                                                 |
| ------------ | ---------------------------------------------------- |
| `lock()`     | 加锁：若锁已被占用，当前线程阻塞，直到获取锁         |
| `unlock()`   | 解锁：释放锁，需确保当前线程持有锁（否则未定义行为） |
| `try_lock()` | 尝试加锁：成功返回`true`，失败返回`false`（不阻塞）  |

**风险**：手动`unlock()`易遗漏（如临界区抛异常），导致死锁，实际开发中优先用**锁管理工具**。

```c++
int num = 0;
mutex mtx;
void func_mutex() {
    mtx.lock();       // 手动加锁
    num++;
    cout << "mutex: num = " << num << endl;
    mtx.unlock();     // 手动解锁
}
```

### 递归互斥锁：`std::recursive_mutex`

**定义**：C++11 标准提供的**递归可重入**互斥锁。

**核心特性**

- 同一线程可多次加锁，内部维护锁计数；
- 解锁次数必须与加锁次数一致，锁才会真正释放；
- 非超时、独占访问。

**适用场景**：递归函数、类成员函数嵌套调用且需要重复加锁的场景。

**注意**：`std::mutex` 在此场景下会死锁（同一线程重复加锁），`recursive_mutex` 有轻微性能开销，非必要不使用。

``` C++
recursive_mutex rec_mtx;
void func_recursive(int n) {
    if (n <= 0) return;

    rec_mtx.lock();   // 第一次加锁
    cout << "recursive_mutex: level " << n << endl;

    func_recursive(n - 1); // 递归，再次加锁

    rec_mtx.unlock(); // 必须对应次数解锁
}
```

### 带超时的互斥锁：`std::timed_mutex`

**定义**：C++11 标准提供的**带超时机制**的非递归互斥锁。

**核心特性**

- 非递归可重入；
- 支持限时等待，避免线程无限阻塞；
- 独占访问。

**适用场景**：需要控制等待时间、避免死锁、高实时性要求的同步场景。

支持超时等待锁，避免线程永久阻塞，核心函数：

- `try_lock_for(时长)`：等待指定时长，获取锁返回`true`，超时返回`false`；
- `try_lock_until(时间点)`：等待到指定时间点，获取锁返回`true`，超时返回`false`。
- **优势**：即使临界区抛异常，`lock_guard` 析构时仍会解锁，保证锁释放。

| 函数               | 功能                                               |
| ------------------ | -------------------------------------------------- |
| `try_lock_for()`   | 在指定时长内尝试加锁，超时未获取则返回 `false`     |
| `try_lock_until()` | 阻塞至指定时间点尝试加锁，超时未获取则返回 `false` |

```c++
timed_mutex t_mtx;
void func_timed() {
    // 尝试锁 100ms，超时返回 false
    if (t_mtx.try_lock_for(100ms)) {
        cout << "timed_mutex: 加锁成功" << endl;
        this_thread::sleep_for(50ms);
        t_mtx.unlock();
    } else {
        cout << "timed_mutex: 超时失败" << endl;
    }
}
```

### 带超时的可递归互斥锁：`std::recursive_timed_mutex`

**定义**：C++11 标准提供的**递归可重入 + 超时**互斥锁。

**核心特性**

- 支持同一线程重复加锁；
- 支持限时获取锁；
- 加锁 / 解锁次数必须匹配。

**适用场景**：递归调用逻辑中，需要超时控制的特殊复杂场景。

```c++
recursive_timed_mutex rec_t_mtx;
void func_rec_timed(int n) {
    if (n <= 0) return;

    if (rec_t_mtx.try_lock_for(50ms)) {
        cout << "recursive_timed_mutex: level " << n << endl;
        func_rec_timed(n - 1);
        rec_t_mtx.unlock();
    }
}
```

### 读写共享互斥锁：`std::shared_mutex`

**定义**：C++17 标准引入的**读写共享互斥锁**，实现**共享读、独占写**模型。

**核心特性**

- **共享模式**：多线程可同时获取共享锁（读锁），并发读取；
- **独占模式**：仅一个线程可获取独占锁（写锁），保证写安全；
- 写锁优先：持有写锁时，无法获取读锁，避免读线程饥饿；
- 无超时机制。

**适用场景**：读操作远多于写操作的高并发场景（如配置读取、缓存查询）。

| 函数                | 功能                                                      |
| ------------------- | --------------------------------------------------------- |
| `lock_shared()`     | 阻塞获取**共享读锁**，多个线程可同时持有                  |
| `unlock_shared()`   | 释放共享读锁                                              |
| `try_lock_shared()` | 非阻塞尝试获取共享读锁，成功返回 `true`，失败返回 `false` |

```c++
shared_mutex share_mtx;
int data = 100;

void read_share() {
    share_mtx.lock_shared();  // 读锁（共享）
    cout << "shared_mutex 读: data = " << data << endl;
    share_mtx.unlock_shared();
}

void write_share(int val) {
    share_mtx.lock();         // 写锁（独占）
    data = val;
    cout << "shared_mutex 写: data = " << data << endl;
    share_mtx.unlock();
}
```

### 带超时机制的读写共享互斥锁`std::shared_timed_mutex`

**定义**：C++17 标准提供的**带超时机制的读写共享互斥锁**。

**核心特性**

- 支持共享读、独占写；
- 支持独占锁 / 共享锁的超时获取；
- 兼容 `shared_mutex` 全部特性。

**适用场景**：读写分离场景中，需要超时控制的高并发、高可用系统。

| 函数                      | 功能                               |
| ------------------------- | ---------------------------------- |
| `lock_shared()`           | 阻塞获取共享读锁                   |
| `unlock_shared()`         | 释放共享读锁                       |
| `try_lock_shared()`       | 非阻塞尝试获取共享读锁             |
| `try_lock_shared_for()`   | 限时获取共享读锁，超时返回 `false` |
| `try_lock_shared_until()` | 定时获取共享读锁，超时返回 `false` |

```c++
shared_timed_mutex st_mtx;

void read_st() {
    if (st_mtx.try_lock_shared_for(100ms)) {
        cout << "shared_timed_mutex 读成功" << endl;
        st_mtx.unlock_shared();
    }
}

void write_st() {
    if (st_mtx.try_lock_for(100ms)) {
        cout << "shared_timed_mutex 写成功" << endl;
        st_mtx.unlock();
    }
}
```

## 智能锁管理工具

C++ 智能锁管理工具是 `<mutex>` 头文件中基于 RAII 原则的锁封装类，核心价值在于**构造加锁、析构解锁**，确保异常安全与死锁预防，避免手动 `lock()`/`unlock()` 导致的锁泄漏。

| 工具类             | 标准  | 核心定位       | 关键特性                                                     | 适用场景                   |
| ------------------ | ----- | -------------- | ------------------------------------------------------------ | -------------------------- |
| `std::lock_guard`  | C++11 | 基础作用域锁   | 构造立即加锁、析构解锁；不可手动控制、不可拷贝移动；轻量高效 | 简单作用域内独占锁定       |
| `std::unique_lock` | C++11 | 灵活独占锁     | 支持延迟 / 尝试 / 超时加锁、手动解锁、所有权转移；适配条件变量 | 复杂同步（条件变量、超时） |
| `std::shared_lock` | C++17 | 共享读锁       | RAII 封装 `std::shared_mutex` 的共享读权限；支持移动、不可拷贝 | 多线程并发读取、读写分离   |
| `std::scoped_lock` | C++17 | 多锁安全管理器 | 一次性锁定多个互斥体；死锁避免算法；析构统一解锁             | 多锁临界区、需避免死锁     |

### `std::lock_guard`：基础作用域锁

- **核心特性**：构造时加锁，析构时解锁，不可手动解锁，不可拷贝 / 移动；
- **适用场景**：简单临界区，生命周期与作用域绑定（推荐首选）。

| 成员函数 | 功能                                                         |
| -------- | ------------------------------------------------------------ |
| 构造函数 | `explicit lock_guard(Mutex& m)`：立即锁定 `m`；`lock_guard(Mutex& m, std::adopt_lock_t)`：接管已锁定的 `m` |
| 析构函数 | 自动调用 `m.unlock()`，释放锁                                |
| 禁用操作 | 无 `lock()`/`unlock()`；不可拷贝、不可移动                   |

```c++
mutex mtx1;
int val = 0;

void func_lock_guard() {
    lock_guard<mutex> lock(mtx1);  // 构造即加锁，离开作用域自动解锁
    val++;
    cout << "lock_guard: val = " << val << endl;
}
```

### `std::unique_lock`：灵活独占锁

- **核心特性**：比`lock_guard`更灵活，支持手动加解锁、超时等待、转移锁所有权；
- **适用场景**：条件变量同步，需超时等待或手动控制锁的场景，锁所有权转移（如函数返回锁）。

| 成员函数      | 功能                                                         |
| ------------- | ------------------------------------------------------------ |
| 构造函数      | 支持 `std::defer_lock`（延迟加锁）、`std::try_to_lock`（尝试加锁）、`std::adopt_lock`（接管锁） |
| `lock()`      | 阻塞加锁，仅在 `std::defer_lock` 构造时可用                  |
| `try_lock()`  | 非阻塞尝试加锁，成功返回 `true`，失败返回 `false`            |
| `unlock()`    | 手动解锁，释放锁所有权                                       |
| `owns_lock()` | 返回是否持有锁                                               |
| `release()`   | 释放锁所有权，返回指向互斥体的指针，后续需手动解锁           |
| 移动语义      | 支持移动构造 / 赋值，转移锁所有权                            |

```c++
mutex mtx2;
void func_unique_lock() {
    unique_lock<mutex> lock(mtx2); // 灵活锁：支持延迟、尝试、解锁、转移
    cout << "unique_lock: 已加锁" << endl;

    lock.unlock();                // 可手动提前解锁
    cout << "unique_lock: 已手动解锁" << endl;

    lock.lock();                  // 可再次加锁
    cout << "unique_lock: 再次加锁成功" << endl;
}
```

### `std::shared_lock`：共享读锁

**核心原理**：RAII 封装 `std::shared_mutex` 的共享读权限，支持多线程并发读取、独占写入。

**适用场景**：多读少写场景，提升并发性能（如缓存、配置读取），配合 `std::shared_mutex`/`std::shared_timed_mutex` 使用。

| 成员函数            | 功能                                                         |
| ------------------- | ------------------------------------------------------------ |
| 构造函数            | 支持 `std::defer_lock`/`std::try_to_lock`/`std::adopt_lock`；共享模式锁定 |
| `lock_shared()`     | 阻塞获取共享读锁                                             |
| `try_lock_shared()` | 非阻塞尝试获取共享读锁                                       |
| `unlock_shared()`   | 释放共享读锁                                                 |
| 移动语义            | 支持移动构造 / 赋值，转移共享锁所有权                        |

```c++
shared_mutex s_mtx;
int data = 100;
void read_shared_lock() {
    shared_lock<shared_mutex> lock(s_mtx); // 共享读：多线程可同时持有
    cout << "shared_lock 读取: data = " << data << endl;
}

void write_unique_lock() {
    unique_lock<shared_mutex> lock(s_mtx); // 写必须独占
    data = 200;
    cout << "unique_lock 写入: data = " << data << endl;
}
```

### `std::scoped_lock`：多锁安全管理器

**核心原理**：一次性锁定多个互斥体，使用死锁避免算法（同 `std::lock`），析构时统一解锁，杜绝多锁死锁。

**适用场景**：多锁临界区，需确保加锁顺序安全，替代 `std::lock` + `std::adopt_lock`，代码更简洁安全。

| 成员函数 | 功能                                                         |
| -------- | ------------------------------------------------------------ |
| 构造函数 | `template <class... Mutexes> explicit scoped_lock(Mutexes&... mutexes)`：锁定所有 `mutexes`；支持 `std::adopt_lock` 接管已锁互斥体 |
| 析构函数 | 对所有互斥体调用 `unlock()`，释放锁                          |
| 禁用操作 | 无 `lock()`/`unlock()`；不可拷贝、不可移动                   |

```c++
mutex mtxA, mtxB;
void func_scoped_lock() {
    scoped_lock lock(mtxA, mtxB); // 一次性锁多个，内部自动避免死锁
    cout << "scoped_lock: 同时锁住 mtxA 和 mtxB" << endl;
}
```

## 全局锁工具

### `std::lock`（多锁同时加锁）

**核心特性**：

1. **死锁安全**：内部采用**未指定顺序的阻塞加锁算法**，确保多个线程按不同顺序请求多把锁时**不会产生死锁**。
2. **批量加锁**：可同时锁定 2 个及以上互斥锁。
3. **原子性**：要么**全部加锁成功**，要么一个都不加锁，不会出现部分加锁状态。
4. **阻塞特性**：若无法获取全部锁，线程会阻塞，直到所有锁可用。
5. **不拥有锁所有权**：仅负责加锁，解锁需手动 / 智能锁完成。

**适用场景**：

- 同时访问**多个共享资源**，需要多锁同步。
- C++17 之前，`std::scoped_lock` 未普及的环境。
- 必须同时获取多锁且**避免死锁**的场景。

### 一次初始化 `std::call_once`

**配套组件**：`std::once_flag`：用于标记函数是否已执行，**全局 / 静态变量**，不可拷贝、不可移动。

**核心特性**：

1. **全局唯一执行**：无论多少线程并发调用，目标函数**只执行一次**。
2. **线程安全**：内部无竞争，无需手动加锁。
3. **高效轻量**：执行完成后几乎无开销，仅读取标志位。
4. **异常安全**：若函数抛出异常，不算执行成功，其他线程可继续尝试执行，直到成功完成一次。
5. **同步语义**：函数执行完成前，所有调用线程都会阻塞。

**适用场景**：

- **单例模式**（线程安全懒汉单例）。
- **初始化操作**：配置加载、资源创建、SDK 初始化。
- 任何**全局唯一、仅执行一次**的逻辑。

在某些场景下（如单例模式、全局配置加载），我们需要确保某段初始化代码在整个程序生命周期中**只被执行一次**，即使有多个线程同时尝试执行。C++11 提供了 `std::call_once` 和 `std::once_flag` 来优雅地解决此问题，无需手动加锁。

### `std::try_lock`（依次尝试锁定多个互斥锁）

**功能**：非阻塞地**依次尝试锁定**多个互斥锁。

- 若全部加锁成功：返回 `-1`
- 若某一把加锁失败：**立即解锁已成功锁住的所有锁**，并返回该锁的下标（从 0 开始）
- 不会阻塞线程

**典型场景**：需要同时获取多把锁，但不想阻塞，失败则执行其他逻辑。



# 原子操作

在 `<atomic>` 头文件中引入了**原子操作（Atomic Operation）** 机制，核心用于实现无锁的线程同步 —— 保证对共享数据的操作 “不可中断”，从硬件层面避免数据竞争，性能远高于互斥锁（无需上下文切换）。原子操作是轻量级同步的首选方案，适用于简单的共享数据修改（如计数器、标志位）。

原子操作的核心价值：**单个操作的原子性**—— 对原子类型的读写 / 修改操作，CPU 会保证其在执行过程中不被其他线程打断，无需加锁即可实现同步。

## 背景

**互斥锁的局限性**：互斥锁虽能解决数据竞争，但存在明显缺陷：

1. **性能开销**：加锁 / 解锁涉及线程上下文切换，高频调用时性能损耗大；
2. **粒度问题**：锁只能保护一段代码（临界区），无法精准保护单个变量操作；
3. **死锁风险**：多锁场景易引发死锁。

## 核心概念与基础语法

**原子类型（std::atomic）**

`std::atomic` 是模板类，封装了基础类型（如`int`、`bool`、指针），使其支持原子操作。预定义了常用原子类型别名。

| 原子类型别名       | 对应模板类型            | 适用场景               |
| ------------------ | ----------------------- | ---------------------- |
| `std::atomic_bool` | `std::atomic<bool>`     | 布尔标志位（如 ready） |
| `std::atomic_int`  | `std::atomic<int>`      | 整数计数器             |
| `std::atomic_long` | `std::atomic<long>`     | 长整数计数器           |
| `std::atomic<T*>`  | `std::atomic<指针类型>` | 原子指针操作           |

**核心原子操作**

原子类型支持两类操作：

- **基础操作**：加载（`load()`）、存储（`store()`）、交换（`exchange()`）；
- **复合操作**：比较并交换（`compare_exchange_weak`/`strong`）、加减（`fetch_add`/`fetch_sub`）等。

所有操作均为原子性，且可指定**内存序（Memory Order）**（控制 CPU 缓存 / 指令重排，默认`memory_order_seq_cst`，即顺序一致性，最严格也最常用）。

**示例（原子计数器）**

```c++
// 原子计数器
atomic_int count(0);
void increment() {
    for (int i = 0; i < 1000000; ++i) {
        // 被重载为原子操作，无需加锁，性能比mutex + int高一个数量级。
        count++; // 等价于count.fetch_add(1)，原子自增
    }
}
thread t1(increment);
thread t2(increment);
t1.join();
t2.join();
cout << "最终计数：" << count << endl; // 输出2000000，无数据竞争
```

## 核心原子操作

### 基础读写操作

| 成员函数       | 功能                                           |
| -------------- | ---------------------------------------------- |
| `load(mo)`     | 原子加载值（读取），默认`memory_order_seq_cst` |
| `store(v, mo)` | 原子存储值（写入），将值`v`存入原子变量        |
| `exchange(v)`  | 原子交换：存入`v`，返回旧值                    |

```c++
atomic_bool flag(false);
// 线程1：存储值
void set_flag() {
    flag.store(true); // 原子写入true
}
// 线程2：加载值
void check_flag() {
    while (!flag.load()) { // 原子读取值
        this_thread::yield(); // 主动让出CPU，减少空转
    }
    cout << "标志位已置为true" << endl;
}
thread t1(set_flag);
thread t2(check_flag);
t1.join();
t2.join();
```

### 复合算术操作

| 成员函数       | 功能                                                      |
| -------------- | --------------------------------------------------------- |
| `fetch_add(n)` | 原子加`n`，返回操作前的旧值（等价于`n += x`，但返回旧值） |
| `fetch_sub(n)` | 原子减`n`，返回操作前的旧值                               |
| `fetch_and(n)` | 原子按位与`n`，返回旧值                                   |
| `fetch_or(n)`  | 原子按位或`n`，返回旧值                                   |
| `fetch_xor(n)` | 原子按位异或`n`，返回旧值                                 |

**语法糖**：C++ 重载了运算符（如`++`、`+=`），等价于对应的复合操作：

- `count++` → `count.fetch_add(1)`（返回旧值）；
- `++count` → `count.fetch_add(1) + 1`（返回新值）；
- `count += 5` → `count.fetch_add(5)`。

```c++
atomic_int num(10);
int old_val = num.fetch_add(5); // old_val=10，num=15
num += 3; // num=18
int new_val = ++num; // new_val=19，num=19
```

### 比较并交换（CAS，Compare-And-Swap）

CAS 是原子操作的核心，也是无锁编程的基础。

**核心逻辑：**若原子变量的当前值等于 “预期值”，则将其更新为 “新值”；否则不修改，返回 false。

**CAS 的价值**：实现复杂的原子逻辑（如条件更新），无需加锁。

**核心函数**

- `compare_exchange_weak(expected, desired, mo)`：

  - 弱版本：可能因 CPU 伪唤醒失败（即使值相等），需配合循环使用；
  - 返回值：是否交换成功；
  - 若失败，`expected`会被更新为原子变量的当前值。
  
- `compare_exchange_strong(expected, desired, mo)` ：

  - 强版本：仅当值不相等时失败，无需循环（性能略低）。

**CAS 实现自定义原子操作**

```c++
atomic_int val(0);
// 用CAS实现“仅当val=0时，将其设为100”
void cas_operation() {
    int expected = 0; // 预期值
    int desired = 100; // 目标值
    // 弱CAS需循环（处理伪唤醒）
    while (!val.compare_exchange_weak(expected, desired)) {
        // 失败时，expected已被更新为当前值，重置为0继续尝试
        expected = 0;
    }
    cout << "CAS成功，val=" << val << endl; // 输出100
}
thread t(cas_operation);
t.join();
```

### 无锁原子标志 (std::atomic_flag)

`std::atomic<bool>` 虽然常用，但标准**不保证**其在所有平台上都是无锁 (lock-free) 实现的（某些架构可能需要内部锁）。
C++11 中，**唯一保证无锁**的原子类型是 `std::atomic_flag`。它的功能非常精简，常用于实现底层的自旋锁 (Spinlock)。

*   **特性**：
    *   必须是平凡可构造的，通常使用宏 `ATOMIC_FLAG_INIT` 初始化。
    *   不支持 `load()` 或 `store()` 操作。
    *   仅支持两个操作：
        1.  `test_and_set()`: 原子地读取当前值并设置为 `true`，返回旧值。
        2.  `clear()`: 原子地设置为 `false`。

*   **代码示例：实现一个简单的自旋锁**
    

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <iostream>

class SpinLock {
    std::atomic_flag flag = ATOMIC_FLAG_INIT; // 初始化为 false (未锁定)
public:
    void lock() {
        // 忙等待：如果 flag 已经是 true (被占用)，则循环测试
        while (flag.test_and_set(std::memory_order_acquire)) {
            // 可以在这里加入 cpu_relax() 或 yield() 减少功耗
        }
    }
    void unlock() {
        flag.clear(std::memory_order_release);
    }
};
SpinLock mutex;
int shared_data = 0;
void worker() {
    for (int i = 0; i < 1000; ++i) {
        mutex.lock();
        ++shared_data;
        mutex.unlock();
    }
}
std::vector<std::thread> threads;
for (int i = 0; i < 10; ++i) threads.emplace_back(worker);
for (auto& t : threads) t.join();
std::cout << "Result: " << shared_data << std::endl; // 预期 10000
```

**注意**：自旋锁适合临界区代码执行时间极短的场景。如果持锁时间长，忙等待会浪费大量 CPU 资源，此时应优先使用 `std::mutex`。

## 原子操作 vs 互斥锁

| 特性       | 原子操作                           | 互斥锁（std::mutex）             |
| ---------- | ---------------------------------- | -------------------------------- |
| 实现层面   | 硬件指令（如 x86 的 LOCK 前缀）    | 操作系统内核调度                 |
| 性能       | 极高（无上下文切换）               | 较低（上下文切换开销）           |
| 适用场景   | 简单操作（计数器、标志位、CAS）    | 复杂临界区（多步操作、多个变量） |
| 死锁风险   | 无                                 | 有（多锁场景）                   |
| 使用复杂度 | 低（简单操作）/ 高（CAS / 内存序） | 低（RAII 工具）                  |
| 功能覆盖   | 仅支持单个变量的原子操作           | 支持任意临界区保护               |

**选型建议**

- **优先用原子操作**：共享数据仅需单个原子操作（如`count++`、`flag=true`）；
- **用互斥锁**：共享数据需多步操作（如先读再改再写）、或需保护多个变量。

# 内存序

内存序是原子操作（`<atomic>`）的核心高级特性，用于**控制 CPU 指令重排和多线程间的内存可见性**。在多核 CPU 架构下，每个核心有独立缓存，线程对内存的读写可能因缓存同步、指令重排导致 “看到” 的内存状态不一致；内存序通过标准化的规则，约束原子操作的执行顺序和缓存可见性，是无锁编程的关键基础。

内存序的核心价值：**通过显式规则约束操作顺序和缓存同步，保证多线程间的内存可见性**。

## 背景

现代 CPU 为提升性能会做两项优化，这在多线程下会破坏原子操作的 “直观顺序”：

1. **指令重排**：CPU / 编译器会调整指令执行顺序（保证单线程语义不变），但多线程下会导致操作顺序错乱；
2. **缓存不一致**：多核 CPU 的缓存未及时同步，线程 A 修改的内存值，线程 B 可能无法立即看到。

```c++
// 无内存序的问题
atomic<bool> flag(false);
int data = 0;
// 线程1：先写data，再置flag
void thread1() {
    data = 100;          // 普通写操作
    flag.store(true);    // 原子存储（默认内存序）
}
// 线程2：先查flag，再读data
void thread2() {
    while (!flag.load()) {} // 原子加载
    cout << "data = " << data << endl; // 预期100，实际可能是0！
}
thread t1(thread1);
thread t2(thread2);
t1.join();
t2.join();
```

**问题根源**：

- 编译器 / CPU 可能将`thread1`的`data=100`和`flag.store(true)`重排；
- 即使未重排，`data=100`的修改可能仅存在于线程 1 的缓存，线程 2 无法立即看到。

## 核心概念与核心语义

| 内存序                 | 内存序      | 核心语义                                                   | 同步保证                                                     | 典型场景               |
| ---------------------- | :---------- | ---------------------------------------------------------- | ------------------------------------------------------------ | ---------------------- |
| `memory_order_relaxed` | 松散序      | 仅保证原子性，无重排与同步约束                             | 无 Synchronizes-with，仅自身原子性                           | 独立计数器             |
| `memory_order_release` | 释放序      | 前置读写不重排到存储后                                     | 释放前所有写对获取同一原子的线程可见                         | 生产者                 |
| `memory_order_acquire` | 获取序      | 后续读写不重排到加载前                                     | 看到释放同一原子的所有写                                     | 消费者                 |
| `memory_order_consume` | 消费序      | 仅对数据依赖操作生效，依赖操作不重排到加载前（不推荐使用） | 释放线程中依赖该原子的写，对消费线程中依赖该原子加载结果的操作可见 | 指针发布-订阅          |
| `memory_order_acq_rel` | 获取-释放序 | 兼具 acquire 和 release 语义（不常用）                     | 加载侧 acquire，存储侧 release                               | 读-改-写同步           |
| `memory_order_seq_cst` | 顺序一致序  | 最严格，全局总顺序，所有线程观测一致（默认内存序）         | acquire + release + 全局总序                                 | 需强一致性的核心同步点 |

### `memory_order_relaxed`（松散内存序）

**核心定义**

- **只保证原子性**
- **不提供任何线程间同步 / happens-before 关系**
- **不禁止任何指令重排**

**重排规则**

- 前后普通读写 **可以随意重排** 到原子操作前后
- 多个 relaxed 原子操作之间 **也可能重排**（除非是对**同一个原子变量**的操作）

**可见性保证**：**无全局可见性保证**
一个线程的 relaxed 写入，另一个线程可能**很久后才看到**，理论上甚至可以一直不可见（实际由缓存一致性决定，但标准不保证）。

**适用场景**

- 无同步需求的**纯计数器**
- 统计、采样、无锁只读指标
- 不需要依赖其他变量状态、只关心最终结果

**性能**：**最快**，无 CPU 内存屏障开销。

```c++
void test_relaxed() {
    for (int i = 0; i < 1000; ++i) {
        cnt.fetch_add(1, memory_order_relaxed);
    }
}
thread t1(test_relaxed), t2(test_relaxed);
t1.join(); t2.join();
cout << "relaxed 计数器最终值: " << cnt << endl;
```

### `memory_order_release`（释放内存序）

**核心定义**

- **写语义**，只能用于**存储操作 store / exchange / fetch_* 等写型原子操作**
- 自带**单向内存屏障**：
  **在本线程中，所有 release 之前的读写操作，不允许重排到 release 之后**
- 建立 **释放语义**：一旦该原子写完成，**此线程之前的所有内存修改**，对成功**acquire 同一原子变量**的线程可见。

**重排规则**

- 禁止：前面的读写 → 重排到 release 之后
- 允许：后面的读写 → 重排到 release 之前

**可见性保证**

- 不保证对所有线程全局可见
- 只保证：**被对应 acquire 读到时**，之前的修改一定可见

**适用场景**

- 生产者通知消费者：写完数据后，设置标志位
- 与 acquire **成对使用**，构成获取-释放模型

### `memory_order_acquire`（获取内存序）

**核心定义**

- **读语义**，只能用于**加载操作 load / CAS 等读型原子操作**
- 自带**单向内存屏障**：
  **本线程中，所有 acquire 之后的读写，不允许重排到 acquire 之前**
- 一旦读到由 release 写入的值，就会**同步**该线程 release 前的所有修改。

**重排规则**

- 禁止：后面的读写 → 重排到 acquire 之前
- 允许：前面的读写 → 重排到 acquire 之后

**可见性保证**

- 只有当 acquire 读到**由 release 写入的值**时，才能看到对方线程之前的所有修改
- 若没读到对应值，则无任何同步保证

**适用场景**

- 消费者等待生产者标志位
- 自旋等待、无锁队列读取端

```c++
void test_release() {
    x.store(111, memory_order_relaxed);       // 前面的写
    y.store(222, memory_order_relaxed);
    // release：之前所有写，不会重排到这条之后
    x.store(999, memory_order_release);
}
void test_acquire() {
    // 等待看到 release 写入的值
    while (x.load(memory_order_acquire) != 999);
    // 此时一定能看到 y=222
    assert(y.load(memory_order_relaxed) == 222);
}
thread t3(test_release), t4(test_acquire);
t3.join(); t4.join();
```

### `memory_order_consume`（消费内存序）

**核心定义**

- 比 acquire **更轻量**的读内存序
- 只对**数据依赖**的操作提供同步（指针、索引链）
- 不阻止无关指令重排，理论上性能优于 acquire

**现状**

- C++11 设计，但**编译器实现极难**
- GCC/Clang 实际都**将 consume 当成 acquire 处理**
- C++20 已明确标记为**不推荐使用，基本废弃**
- 实际开发中**永远不要用**，直接用 acquire 替代

```c++
void test_consume() {
    int val = 1234;
    ptr.store(&val, memory_order_release);
}
void run_consume() {
    int* p; // consume 只同步与指针有数据依赖的操作
    while (!(p = ptr.load(memory_order_consume)));
    assert(*p == 1234);// 依赖 p，所以能看到 *p = 1234
}
thread t5(test_consume), t6(run_consume);
t5.join(); t6.join();
```

### `memory_order_acq_rel`（获取-释放内存序）

**核心定义**

- **同时具备 acquire + release 语义**
- 只能用于**“读-改-写”原子操作**：fetch_add、exchange、compare_exchange_strong/weak
- 操作前：相当于 acquire（禁止后续重排到前面）
- 操作后：相当于 release（禁止前面重排到后面）

**重排规则**

- 禁止前后代码“穿过”该原子操作
- 但**不建立全局总序**

**适用场景**

- 无锁数据结构中的 CAS 循环、节点出入队
- 既需要读同步，又需要写同步的**单次原子操作**
- 实际工程中**极少手写**，一般用 `seq_cst` 或分开 acquire/release 替代

```c++
void test_acq_rel() {
    // 一次操作同时带 acquire(前) + release(后)
    int old = cnt.fetch_add(1, memory_order_acq_rel);
    (void)old;
}
cnt = 0;
thread t7(test_acq_rel), t8(test_acq_rel);
t7.join(); t8.join();
cout << "acq_rel fetch_add 结果: " << cnt << endl;
```

### `memory_order_seq_cst`（顺序一致性）

`memory_order_seq_cst`（原子操作**默认内存序**）

**核心语义**

1. 所有线程看到的原子操作顺序，与程序“源码顺序”完全一致
2. 所有原子操作构成**全局单一总序**
3. 自带完整内存屏障，强制缓存一致性同步

**类比**：所有线程按同一“全局时钟”执行原子操作，顺序绝对一致。

**优势**：最直观、最安全，完全符合直觉

**劣势**：性能最差（全屏障、禁止重排、强制全局同步）

```c++
atomic<int> a{0}, b{0};
void thread_seq1() {
    a.store(1, memory_order_seq_cst);
    b.store(1, memory_order_seq_cst);
}
void thread_seq2() {
    while (b.load(memory_order_seq_cst) == 0);// 如果看到 b=1，则一定看到 a=1
    assert(a.load(memory_order_seq_cst) == 1);
}
thread t9(thread_seq1), t10(thread_seq2);
t9.join(); t10.join();
```

## 核心使用规则

**操作类型与内存序的匹配**

| 原子操作类型         | 支持的内存序                            | 典型场景           |
| -------------------- | --------------------------------------- | ------------------ |
| 加载（load）         | `seq_cst / acquire / consume / relaxed` | Acquire 读、松散读 |
| 存储（store）        | `seq_cst / release / relaxed`           | Release 写、松散写 |
| 读写（CAS/exchange） | `seq_cst / acq_rel / relaxed`           | 原子交换、条件更新 |

**关键原则：“先释放，后获取”**：获取 - 释放语义的核心是 “Release 操作在前，Acquire 操作在后”，且二者必须操作**同一个原子变量**，否则约束失效。

**错误示例（不配对）**

```c++
atomic<bool> flag1(false), flag2(false);
int data = 0;
// 线程1：Release flag1
data = 100;
flag1.store(true, memory_order_release);
// 线程2：Acquire flag2（与flag1无关）
while (!flag2.load(memory_order_acquire)) {}
cout << data << endl; // 可能看到0！
```

**避免 “数据竞争” 的核心**

内存序仅约束**原子操作**的顺序 / 可见性，普通变量的读写仍需满足：

- 若一个线程写普通变量，另一个线程读 / 写该变量，必须通过 “Release-Acquire 对” 或顺序一致性保证可见性；
- 否则会触发 “数据竞争”（未定义行为）。
