### 一、基础概念类
#### 问题1：C++ 中空类的大小为什么是1字节？如果空类作为基类，大小可能还是1吗？
**回答思路**：先解释空类大小的核心原因，再补充空基类优化（EBCO）的细节。
1. 空类大小为1字节的核心原因：C++ 标准要求每个对象必须有唯一的内存地址，1字节是最小可寻址单元，用于区分不同的空类对象实例。
2. 空类作为基类时，大小不一定为1：C++11 起编译器支持空基类优化（EBCO），若派生类有自身数据成员，编译器会优化掉基类的1字节开销，仅保留派生类成员的大小（例如 `class Derived : public Empty { int x; }` 的大小为4字节）；但如果派生类也是空类，或未触发 EBCO（如空类作为成员而非基类），则仍会保留1字节。
3. 补充：C++17 的 `[[no_unique_address]]` 属性可对空类成员做类似优化，进一步减少内存占用。

#### 问题2：静态成员（数据/函数）与非静态成员的核心区别？静态数据成员存在哪里？
**回答思路**：从存储位置、访问方式、this指针、sizeof影响四个维度对比，明确静态成员的底层特性。

核心区别：
1. 存储位置：静态数据成员存于全局/静态存储区（程序生命周期内存在），非静态成员存于对象实例的内存中；静态成员函数存于代码段，与普通函数无本质区别。
2. this指针：静态成员函数无this指针，无法直接访问非静态成员；非静态成员函数隐含this指针，指向调用对象。
3. 访问方式：静态成员可通过类名（`Class::static_mem`）或对象访问，本质一致；非静态成员必须通过对象/指针/引用访问。
4. sizeof影响：静态数据成员不计入类对象的大小，仅非静态成员（含vptr）会影响sizeof结果。

静态数据成员的存储：全局/静态存储区（.data 或 .bss 段），而非栈/堆，且整个程序中仅一份实例。

### 二、虚函数与多态核心
#### 问题3：虚函数的实现原理（vptr + vtable）？构造/析构函数中调用虚函数为什么不会触发多态？
**回答思路**：先拆解 vptr/vtable 的核心机制，再分析构造/析构时 vptr 的生命周期。
1. 虚函数底层实现：
   - 编译器为每个含虚函数的类生成唯一的虚表（vtable）：存储该类所有虚函数的地址，位于只读数据段（.rodata）。
   - 每个类对象会被插入一个隐藏的虚指针（vptr）：指向所属类的 vtable，64位系统下占8字节，通常位于对象内存起始位置。
   - 动态绑定流程：通过基类指针/引用调用虚函数时，先取对象的vptr找到vtable，再根据编译期确定的索引找到目标函数地址，最终调用（多一次间接内存访问）。

2. 构造/析构中调用虚函数无多态的原因：
   - 构造时：vptr 按继承顺序逐步初始化——先调用基类构造，vptr 指向基类vtable；再调用派生类构造，vptr 重置为派生类vtable。因此基类构造中调用虚函数，仅能调用基类版本。
   - 析构时：vptr 按相反顺序重置——先析构派生类（vptr 指向派生类vtable），再析构基类（vptr 重置为基类vtable）。因此基类析构中调用虚函数，仅能调用基类版本。
   - 本质：构造/析构过程中，对象的“实际类型”被限定为当前正在构造/析构的类，无法体现多态。

#### 问题4：为什么需要虚析构函数？如果基类析构函数非虚，会有什么问题？
**回答思路**：结合对象内存释放流程，说明资源泄漏的核心原因。
1. 虚析构函数的必要性：当通过基类指针删除派生类对象时，需保证派生类析构函数被调用，否则会导致派生类持有的资源泄漏。
2. 非虚析构的问题：
   - 编译器会静态绑定析构函数——基类指针删除派生类对象时，仅调用基类析构函数，派生类析构函数被跳过。
   - 后果：派生类的非静态数据成员（如堆内存、文件句柄）无法被释放，造成内存泄漏/资源泄露。
3. 补充：若类无需被继承，析构函数无需声明为虚（避免额外的vptr开销）；若类作为基类，建议默认声明为虚析构（C++11 可写 `virtual ~Class() = default;`）。

#### 问题5：虚函数默认参数是静态绑定还是动态绑定？举个例子说明陷阱。
**回答思路**：明确绑定规则，结合代码示例说明易错点。
1. 核心规则：虚函数的默认参数是静态绑定（编译期确定），仅由指针/引用的静态类型决定；而函数体是动态绑定（运行期确定）。

2. 示例陷阱：

   ```c++
   class Base {
   public:
       virtual void func(int x = 10) { cout << "Base::func, x=" << x << endl; }
   };
   class Derived : public Base {
   public:
       void func(int x = 20) override { cout << "Derived::func, x=" << x << endl; }
   };
   int main() {
       Base* ptr = new Derived();
       ptr->func(); // 输出：Derived::func, x=10
       delete ptr;
   }
   ```

3. 原因：ptr 的静态类型是 Base*，因此默认参数取 Base 的 10；函数体因动态绑定调用 Derived::func，最终出现“函数体是派生类、参数是基类”的矛盾。

4. 建议：重写虚函数时不要修改默认参数，避免语义混淆。

### 三、继承与对象布局
#### 问题6：多继承下的对象布局有什么特点？为什么需要 Thunk 技术？
**回答思路**：先说明多继承的多 vptr 特性，再解释 Thunk 解决的 this 指针调整问题。

1. 多继承的对象布局特点：
   - 派生类对象包含多个基类子对象，每个有虚函数的基类都会对应一个独立的 vptr（指向各自的“子虚表”）。
   - 内存布局按继承顺序排列：例如 `Derived : public Base1, public Base2`，先存 Base1 的 vptr + 成员，再存 Base2 的 vptr + 成员，最后存派生类自身成员。

2. Thunk 技术的必要性：
   - 问题：当通过非第一个基类指针（如 Base2*）调用派生类虚函数时，this 指针初始指向 Base2 子对象的起始位置，而非派生类对象的起始位置，直接调用会导致 this 指针错误。
   - Thunk 作用：编译器生成的小型辅助代码，调用虚函数前调整 this 指针（如减去 Base2 子对象的偏移量），使其指向派生类对象起始位置，再调用实际函数。
   - 示例：Derived 继承 Base1（偏移0）和 Base2（偏移8），通过 Base2* 调用 g() 时，Thunk 先将 this 减8，再调用 Derived::g()。

#### 问题7：什么是对象切片（Slicing）？如何避免？
**回答思路**：定义切片现象，说明原因，给出解决方案。
1. 对象切片定义：将派生类对象按值赋值/传递给基类对象时，派生类独有的成员被截断，仅保留基类子对象，且 vptr 被重置为基类虚表，导致多态失效。
2. 示例：
   void func(Base b) { b.func(); } // 值传递，发生切片
   Derived d;
   func(d); // 调用 Base::func，而非 Derived::func
3. 避免方法：
   - 始终使用指针或引用传递多态类型（如 `void func(Base& b)` 或 `void func(Base* b)`）。
   - 若需值语义，可使用智能指针（如 `std::unique_ptr<Base>`）封装派生类对象。

#### 问题8：虚基类解决了什么问题？其实现机制（Itanium ABI）是什么？
**回答思路**：先说明菱形继承的问题，再解释虚基类的底层实现。
1. 虚基类的作用：解决菱形继承（Diamond Inheritance）中的二义性和数据冗余——确保最顶层基类在派生类中仅存在一份实例（而非每个中间基类各存一份）。
2. Itanium ABI 下的实现机制：
   - 虚基类子对象的偏移量存储在虚表的负索引处（vptr[-2] 指向偏移量数组）。
   - 派生类对象访问虚基类成员时，先通过 vptr 找到偏移量数组，计算出虚基类子对象的实际地址，再访问成员。
   - 布局特点：虚基类子对象通常位于派生类对象的末尾，非虚基类在前。
3. 补充：虚基类的构造函数由最派生类直接调用，中间基类对虚基类的构造调用会被忽略。

### 四、工程实践与性能
#### 问题9：虚函数有哪些性能开销？如何优化？
**回答思路**：量化开销（内存+时间+微架构），给出具体优化策略。
1. 虚函数的性能开销：
   - 内存开销：每个对象多一个 vptr（64位8字节）；每个类的虚表占少量只读内存（可忽略）。
   - 时间开销：每次调用多2-3次内存访问（vptr→vtable→函数地址）；无法内联（编译期无法确定函数地址）。
   - 微架构开销：间接跳转清空CPU流水线、缓存未命中、BTB预测失败，高频调用时损耗明显。

2. 优化策略：
   - 避免不必要的虚函数：仅在需要多态时声明虚函数。
   - 使用 final 关键字：对无需重写的虚函数/类加 final，编译器可优化动态绑定（甚至内联）。
   - 静态多态（CRTP）：通过奇异递归模板模式实现编译期多态，无运行时开销。
     示例：
     template <typename Derived>
     class Base {
     public:
         void func() { static_cast<Derived*>(this)->func_impl(); }
     };
     class Derived : public Base<Derived> { public: void func_impl() {} };
   - 集中调用虚函数：减少缓存未命中；利用 PGO 优化热路径虚函数。
   - 纯虚接口+非虚实现：对外暴露纯虚接口，内部用非虚函数实现，平衡扩展性与性能。

#### 问题10：标准布局（Standard Layout）和平凡可复制（Trivially Copyable）的条件与作用？
**回答思路**：分别说明两类类型的约束和工程价值。
1. 标准布局（Standard Layout）：
   - 条件：① 所有非静态成员访问控制一致；② 无虚函数/虚基类；③ 继承树中最多一个类有非静态成员；④ 成员和基类均为标准布局。
   - 作用：与C结构体内存兼容，可使用 offsetof 宏，对象地址等于第一个成员地址，适合跨语言交互。

2. 平凡可复制（Trivially Copyable）：
   - 条件：① 无用户自定义的拷贝/移动构造、赋值、析构；② 无虚函数/虚基类；③ 成员和基类均为平凡可复制。
   - 作用：可通过 memcpy 安全拷贝，支持原子操作（std::atomic），适合高性能内存操作（如内存池、序列化）。

3. 示例：纯C风格结构体（如 `struct Data { int a; double b; }`）既是标准布局也是平凡可复制。

### 五、进阶拓展
#### 问题11：成员指针（数据/函数）的底层实现与普通指针有何不同？
**回答思路**：分数据成员指针和函数成员指针说明。
1. 数据成员指针：
   - 存储的是成员在对象中的偏移量（而非绝对地址），size_t 类型。
   - 若类含虚函数，第一个数据成员的偏移量为 vptr 大小（64位8字节）。
   - 注意：`(size_t)&(((MyClass*)nullptr)->*data_ptr)` 是未定义行为，标准布局类型应使用 offsetof 宏。

2. 成员函数指针：
   - 单继承非虚函数：存储函数地址（8字节）。
   - 多继承/虚继承非虚函数：存储函数地址 + this 指针调整量（16字节）。
   - 虚函数：存储虚表索引（8/16字节），调用时通过 vptr + 索引找函数地址。
   - 核心区别：普通指针指向内存绝对地址，成员指针需结合对象实例（this）才能确定实际地址。

#### 问题12：动态库边界使用虚函数可能遇到什么问题？如何解决？
**回答思路**：说明虚表不兼容问题，给出工程解决方案。
1. 核心问题：基类在动态库A，派生类在动态库B，若A升级后虚表布局变化（如新增虚函数、调整顺序），B未重新编译会导致虚表索引不匹配，运行时崩溃/函数调用错误。

2. 解决方法：
   - 固定纯虚接口：对外暴露纯虚接口类（如 COM 风格），且永不修改接口的虚函数顺序/数量。
   - 符号版本管理：Linux 下用 `-fvisibility=hidden` 控制符号导出，结合版本脚本（version script）管理虚函数符号。
   - 重新编译依赖：升级动态库时，强制重新编译所有使用该库的模块。
   - 避免跨库虚函数：对外接口使用非虚函数+静态工厂方法，内部实现多态。
