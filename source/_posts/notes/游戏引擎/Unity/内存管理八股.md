# 内存管理

## 值类型和引用类型

- **存储位置**
  - 值类型主要存放在**栈内存**；
  - 引用类型**对象实例存在堆内存**，栈上只存**引用地址**。

- **赋值方式**
  - 值类型赋值是**值拷贝**，两个变量互相独立，修改一个不会影响另一个；
  - 引用类型赋值是**地址拷贝**，两个变量指向堆里同一个对象，改一个另一个也会跟着变。

- **常见类型**
  - 值类型：**struct、int、float、bool、double、枚举、DateTime** 等；
  - 引用类型：**class、string、数组、委托、接口、object** 及所有自定义类。

- **内存与GC**
  - 值类型栈上分配，出作用域自动释放，**不触发GC**；
  - 引用类型堆分配，靠垃圾回收GC回收无用对象，创建过多会产生**GC压力**。

- **补充关键点**
  - string 是**特殊引用类型**，有**字符串驻留、不可变**特性，赋值行为看着像值类型；
  - 结构体是值类型，类是引用类型，Unity里常用结构体**减少堆分配、优化GC**。

## struct和class的区别
- **类型与内存**
  - class 是**引用类型**，实例存在**堆**上，栈只存地址，**会触发GC**；
  
  - struct 是**值类型**，实例存在**栈**上，没有引用地址，**不触发GC**。
  
- **赋值行为**
  - class 赋值是**拷贝引用**，两个变量指向同一个对象，改一个全变；

  - struct 赋值是**完整拷贝值**，两个变量完全独立，互不影响。

- **继承与功能**
  - class 可以**继承、实现接口、写虚函数、重写**，功能完整；

  - struct **不能继承**（除默认继承 ValueType），不能写无参构造，不能析构，功能受限。


- **生命周期与空值**
  - class 可以为 null，使用前**必须判空**；
  - struct **不能为 null**，默认会初始化所有字段为 0/false 等默认值。

- **Unity 实际使用场景**
  - class 用来做**逻辑模块、管理器、单例、UI控制、游戏实体**；
  - struct 用来做**纯数据结构**（比如坐标、颜色、向量、参数结构体），核心作用是**减少堆分配、优化GC**。


## 栈空间和堆空间的区别
- 分配位置：栈由**系统自动管理**内存，堆由**托管堆**分配，受GC管控。
- 分配释放：栈在代码执行进入作用域自动分配，出作用域**立即自动释放**；堆需要手动创建对象分配，不再被引用后由**GC定时回收**。
- 空间大小：栈空间**固定且容量小**，默认容量有限；堆空间**庞大，可动态扩容**，能存放大量对象和大数据。
- 存储内容：栈存放**值类型变量、引用类型的引用地址、函数参数、局部变量、函数调用栈帧**；堆存放**引用类型的实际对象实例、数组内容、字符串实例**。
- 访问速度：栈内存**连续**，访问速度**快**；堆内存**碎片化**，寻址开销大，访问速度更慢。
- 生命周期：栈变量生命周期随代码作用域结束**立刻销毁**；堆对象生命周期不受代码块限制，**只要有引用指向就会一直存活**。
- 溢出风险：栈容易出现**栈溢出**（比如无限递归）；堆不会出现空间溢出，只会存在**内存泄漏、GC卡顿**问题。
- 拷贝机制：栈变量赋值是**完整值拷贝**；堆只拷贝**引用地址**，不复制对象本身。

## 浅拷贝与深拷贝

- **核心本质**
  - 浅拷贝：仅复制对象**表层字段**，引用类型只拷贝**地址**，不新建堆实例；
  - 深拷贝：完整递归复制**所有层级**，值类型、引用类型全部新建独立实例。

- **数据影响**
  - 浅拷贝：若包含嵌套引用类型，原对象与拷贝对象**共享同一个堆对象**，修改互相影响；
  - 深拷贝：原对象与拷贝对象**完全内存隔离**，任意修改互不干扰。

- **适用对象**
  - 浅拷贝：纯值类型结构体、无嵌套引用的简单实体；
  - 深拷贝：含**嵌套class、数组、集合**等多层引用类型的复杂对象。

- **内存与GC**
  - 浅拷贝：无额外堆内存分配，**不增加GC压力**；
  - 深拷贝：会创建新堆对象、新数组实例，产生**额外堆分配与GC开销**。

- **C#内置实现**
  - `MemberwiseClone()` 默认是**浅拷贝**，只复制当前层级所有字段；
  - 深拷贝需手动递归赋值、序列化反序列化、反射遍历等方式自行实现。

- **结合值/引用类型表现**
  - 仅有值类型时：浅拷贝和深拷贝**效果一致**，都是独立副本；
  - 含引用类型成员时：浅拷贝共享引用，深拷贝断开引用、全新实例。

- **Unity实际使用场景**
  - 浅拷贝：复制纯数据**struct、基础配置类**，追求性能少堆分配；
  - 深拷贝：复制**游戏实体、背包数据、技能配置、嵌套对象**，防止原始数据被意外篡改。

## 内存泄漏

## 内存泄漏
- **核心定义**
  - 内存泄漏：**不再使用的对象，依然被引用持有**，无法被GC回收，长期占用堆内存；
  - 本质：**无用对象的引用未清空**，GC判定对象仍存活，永久占用堆空间。

- **发生条件**
  - 仅发生在**引用类型**（class、数组、string、委托等），值类型无泄漏；
  - 堆上对象**存在有效引用**，但业务逻辑已完全不需要使用。

- **常见原因**
  - 静态变量（static）持有大对象/集合，生命周期贯穿程序全程，无法释放；
  - 事件订阅后**未注销**，发布者长期持有订阅者引用，导致对象无法销毁；
  - 集合（List/Dictionary）清空对象时**只删数据不清理引用**，或长期持有无用元素；
  - Unity 场景切换后，**不销毁的单例/静态对象**持有场景内控件、GameObject；
  - 闭包、匿名方法**意外捕获外部引用**，延长对象生命周期；
  - 缓存未设置过期策略，**只增不减**，无限占用内存。

- **危害表现**
  - 堆内存**持续上涨**，可用空间越来越少；
  - GC 频繁触发，造成**程序卡顿、掉帧**；
  - 长期运行会**内存溢出（OOM）**，导致程序崩溃、闪退。

- **排查方式**
  - 使用 VS/ Rider 内存诊断工具，查看**对象引用链**；
  - Unity 使用 Profiler、Memory Profiler 查看未释放对象、引用归属；
  - 重点检查**静态集合、事件、单例、缓存**模块。

- **解决方案**
  - 不用的对象**手动置空引用（=null）**，及时断开引用链；
  - 事件订阅与注销**成对编写**（如OnEnable订阅，OnDisable注销）；
  - 静态集合**定期清理、移除无用数据**，避免无限扩容；
  - 合理使用单例，非必要不使用**全局静态对象**；
  - 缓存增加**清理/过期机制**，用完即释放；
  - Unity 中及时销毁无用对象，避免跨场景持有无用引用。

- **关键特点**
  - 内存泄漏**隐蔽性极强**，短期运行无明显问题，长期运行必出故障；
  - 只影响**堆内存**，栈内存自动释放，不存在泄漏；
  - 是 Unity 游戏、客户端程序**性能优化的重点排查项**。

# 装箱与拆箱

## 核心定义
**装箱**：值类型隐式转为 `object` 或其所实现的接口类型，**分配托管堆内存**，产生GC开销。
**拆箱**：引用类型`object`显式转回原**值类型**，无新堆分配，但存在类型校验与内存拷贝性能消耗。

## 装箱拆箱执行步骤
### 装箱步骤
1. 托管堆分配内存，包含对象头、类型元数据+值类型数据存储空间；
2. 将栈上值类型数据**完整拷贝**至堆内存；
3. 栈上生成**引用地址**，指向堆中装箱对象；
4. 装箱对象由GC统一管理，**产生堆内存分配**。

### 拆箱步骤
1. **严格类型校验**，堆对象与目标值类型不匹配则抛出异常；
2. 定位堆对象内部值类型数据内存地址；
3. 将堆内数据**拷贝回栈内存**；
4. 仅做类型校验与内存拷贝，**不分配新堆内存**。

## 触发装箱场景
**核心本质**：**值类型向引用类型** 转型时，必然触发**装箱**

1. **值类型** 赋值给 **`object`** 变量；
2. **值类型** 传入 **形参为 `object` / 接口** 的方法；
3. **值类型** 存入 **`ArrayList`、`Hashtable` 等非泛型集合**；
4. **结构体** 实例赋值给 **自身实现的接口类型** 变量；
5. 字符串与 **值类型** 直接 **`+` 拼接**；
6. **值类型** 调用 **未重写** 的 `ToString()`/`Equals(object)`/`GetHashCode()`；
7. **闭包、Lambda** 捕获 **局部值类型变量**；
8. **三元运算符** 两侧分别为 **值类型 + 引用类型**；
9. 反射调用时，**值类型** 传入 **`object` 形参**。

值类型的**装箱特例**：值类型作为`ref/out`参数传入方法时，**不会装箱**（直接操作栈内存地址，不转型）。

## 隐式装箱高频场景

1. **值类型** 直接赋值给 **`object`**；
2. **结构体** 直接赋值给 **接口引用**；
3. **值类型** 调用 **未重写的 object 基类虚方法**；
4. **值类型实参** 传入 **`object / 接口` 形参** 的方法；
5. **值类型元素** 直接添加到 **非泛型集合**；
6. 字符串 **`+` 拼接** 混入 **int/struct 等值类型**；
7. **Lambda / 匿名方法** 捕获 **局部值类型变量**；
8. **三元表达式** 自动类型适配，导致 **值类型隐式转型**；
9. 反射调用时，**值类型** 传入 **object 参数**。

## 避免装箱优化方案
1. **优先使用泛型**：用 `List<T>`、`Dictionary<TKey,TValue>` 替代非泛型集合，从根源规避装箱；
2. **规范方法参数**：不用`object/接口`接收值类型，直接定义对应值类型形参；
3. **减少向上转型**：值类型、结构体尽量不赋值给`object`或接口引用变量；
4. **结构体重写虚方法**：自定义struct主动重写 `ToString`、`Equals`、`GetHashCode`，规避默认方法装箱；
5. **优化字符串拼接**：改用字符串插值、`StringBuilder` 替代`+`号拼接；
6. **规避闭包捕获**：Lambda/匿名方法尽量不直接捕获局部值类型；
7. **泛型约束替代接口转型**：通过泛型接口约束处理结构体逻辑，不用接口引用接收结构体实例。

## 代码装箱拆箱检测方式
1. **Unity Profiler**
勾选 `GC Allocations`，帧视图查看**微小频繁堆分配**，结合调用堆栈定位装箱代码行。

2. **IL反编译查看**
使用 dnSpy、ILSpy、ildasm 查看IL指令，出现 **`box`/`unbox`** 即为装箱拆箱操作。

3. **Rider静态检测**
内置性能高亮，自动标注潜在装箱代码，无需运行即可排查。

## 装箱拆箱性能损耗
### 装箱损耗
1. 托管堆**额外分配内存**，包含对象头、类型元数据；
2. 栈到堆的**数据拷贝开销**；
3. 产生临时堆对象，**增加GC压力**，易引发主线程卡顿；
4. 频繁小对象分配造成**内存碎片**，降低分配效率；
5. 底层元数据绑定带来**额外CPU开销**。

### 拆箱损耗
1. **类型安全校验**，产生逻辑判断开销；
2. 堆到栈的**二次内存拷贝**；
3. 无堆分配，但校验、寻址、拷贝均消耗CPU周期。

### 隐性全局损耗
1. 装箱对象堆内存分散，**降低CPU缓存命中率**；
2. 大量装箱拆箱加剧GC频率，引发**帧率波动、卡顿**。

## 内存屏障与装箱拆箱的关系
核心作用：CLR底层保障**装箱操作原子性与多线程可见性**，避免半初始化装箱对象。

1. **装箱依赖内存屏障**
内存屏障禁止指令重排，保证**数据拷贝完成后再赋值引用**。
2. **保障多线程可见性**
屏障刷新缓存，确保其他线程读取**完整装箱对象**。
3. **拆箱无需内存屏障**
拆箱仅读取校验，不修改堆内存，无重排风险。
4. **底层自动处理**
CLR执行`box`指令时**自动插入**，开发者无需手动控制。

## `Nullable<T>` 可空类型装箱特殊规则
1. **无值状态**：`HasValue=false`，装箱直接返回**null**，**不分配堆内存**；
2. **有值状态**：`HasValue=true`，仅对内部**基础值类型**装箱，不装箱Nullable结构体；
3. **拆箱兼容**：可拆箱为原值类型或可空类型，null可直接拆为可空类型；
4. **CLR原生优化**，业务层自动生效，无额外编码。

## Unity GC的原理和触发时机
### GC 基础概念

- **托管内存**：分为**栈内存**与**托管堆内存**。
- **栈内存**：存放**值类型**、局部变量、函数参数、引用地址；出作用域**自动释放**，**不受GC管理**。
- **托管堆**：存放**引用类型**实例（class、数组、string、委托、集合）；生命周期由**GC垃圾回收器**统一管理。
- **GC核心职责**：自动识别**无有效引用**的堆对象，回收占用内存、整理内存碎片，避免手动管理内存。

## GC 完整工作流程

- **挂起主线程**：GC 启动瞬间**暂停主线程、渲染线程、物理线程**所有逻辑，这是 Unity**GC 卡顿、掉帧的根本原因**。
- 标记阶段
  - 从**GC 根对象**出发，深度遍历所有引用链，标记堆中所有**存活可达对象**。
  - **GC 根包含**：静态变量、主线程栈局部变量、全局常驻 GameObject 与组件、托管回调、引擎全局引用。
- **清扫阶段**：遍历整个托管堆，未被标记的对象判定为垃圾，直接回收内存并标记为空闲内存块。
- **压缩阶段**：将所有存活对象向堆低地址平移聚拢，**消除内存碎片**，使堆内存保持连续规整空间，提升后续分配效率。
- **恢复主线程**：GC 整套标记 - 清扫 - 压缩流程结束，恢复主线程正常帧循环逻辑。

## Mono 与 IL2CPP  GC 核心差异

- 底层运行时
  - Mono：解释 + JIT 即时编译，复用**标准.NET 原生 GC**；
  - IL2CPP：IL 代码转 C++ 静态编译，内置**Unity 自研 SGen GC**。
- 分代 GC 支持
  - Mono：**完整支持分代 GC**；
  - IL2CPP：**默认不开启、不支持分代**，采用全局全堆标记清扫。
- 运行时分配开销
  - Mono：泛型运行时实例化、反射频繁、装箱拆箱多，**临时堆对象多、GC 触发频率高**；
  - IL2CPP：编译期提前实例化泛型、剥离冗余反射，**大幅减少隐式堆分配，从源头降低 GC 压力**。
- 平台适配与性能
  - Mono：编辑器兼容好、老平台适配强，**移动端 GC 频繁、卡顿明显**；
  - IL2CPP：全平台原生性能更强、内存占用更低、帧率更稳定，是手游打包**默认首选**。
- 内存整理策略
  - Mono：分代回收 + 代际晋升，碎片化整理频繁，不可预测卡顿多；
  - IL2CPP：全局一次性标记清扫，逻辑极简，**GC 触发时机更可控、卡顿更集中**。

## 标准 .NET 分代 GC 底层原理

- **分代内存划分**：托管堆逻辑划分为**0 代、1 代、2 代**三个层级。
- **对象分配规则**：新创建引用类型对象**优先分配到 0 代**；0 代空间最小、回收频率最高、单次开销最低。
- **代际晋升机制**：经过多次 0 代 GC 仍存活的长期对象，自动**晋升至 1 代**；1 代对象长期存活再晋升至**2 代**。
- **分代设计核心思想**：利用**弱分代假设**—— 大多数对象生命周期极短，只高频回收 0 代短期对象，减少全堆扫描。
- **分代优势**：无需每次 GC 都扫描整个托管堆，**回收效率高、单次耗时短、CPU 开销低**；长期存活对象只低频扫描。

### Unity IL2CPP 为什么不分代

- **实时游戏帧循环要求**：分代的**代际晋升、分区管理、碎片整理**会引入不可预测卡顿，影响帧率稳定。
- **移动端硬件限制**：手机CPU弱、内存小，分代额外内存分区和管理逻辑**增加CPU与内存开销**。
- **Unity GC设计取舍**：放弃分代精细回收，改用**全局标记清扫**，逻辑更简单、卡顿时机更可控，适配手游实时性。
- **减少隐式分配优先**：Unity引擎从底层优化，通过引擎机制**减少临时堆对象产生**，替代分代带来的回收效率。

## GC 触发时机全场景

### 自动触发

- 托管堆剩余空闲空间不足，新建 class、数组、集合等引用类型**申请堆内存失败**时自动触发。
- 单帧内频繁产生**隐式临时引用对象**：字符串拼接、值类型装箱拆箱、foreach 迭代枚举、匿名委托 / Lambda、临时 List/Dictionary。
- 场景加载 / 卸载：`LoadScene`/`UnloadScene` 流程中引擎**主动强制执行一次 GC**，回收场景孤立对象。
- 托管堆内存占用达到 Unity 内部阈值，后台自动触发回收。

### 手动触发

- 代码主动调用 `GC.Collect()` 强制立即执行全量垃圾回收。
- 最佳实践：在**关卡切换、界面跳转、黑屏过渡、游戏暂停**等非关键帧手动调用，把 GC 卡顿前置规避战斗帧卡顿。

### 析构函数调用规则与时机

- **归属主体**：析构函数由**GC垃圾回收器**负责调用，开发者不能手动主动调用。
- **调用时机**：对象被GC判定为垃圾对象、标记完成后**正式回收内存之前**自动执行。
- **执行特性**
  - 对象断开引用后**不会立刻执行析构函数**，必须等待下一次GC触发才会执行。
  - 调用时机**不确定、顺序不可控**，不依赖主线程时序。
- **开发规范**
  - 禁止在析构函数中做**资源释放、文件关闭、网络断开、Unity组件操作**。
  - Unity资源统一用 `OnDestroy`、手动Dispose、对象池管理，**杜绝依赖析构函数**。

## GC 卡顿核心根源与优化本质

- **卡顿根源**：GC 执行期间**挂起主线程**，逻辑、动画、物理、渲染全部停滞。
- **优化核心思路**：不依赖 GC 回收优化，重点**减少堆分配、减少临时对象、减少引用滞留**，从源头降低 GC 触发次数。
- **常见 GC 诱因**：字符串频繁拼接、装箱拆箱、临时集合、每帧 new 对象、静态集合无限累加、事件订阅不注销。
