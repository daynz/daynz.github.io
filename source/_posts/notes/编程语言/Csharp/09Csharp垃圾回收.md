# GC 垃圾回收

[toc]

## 垃圾的产生

### 核心定义

GC 中的**垃圾**，指托管堆中**无有效引用指向、程序逻辑不再使用、后续代码无法访问**的托管对象。这类对象占用的堆内存失去存在意义，无法被业务逻辑复用，属于无效占用内存，需要由 GC 识别并回收释放，避免内存持续堆积。

### 产生：引用失效是垃圾形成的核心条件

托管对象只要存在**有效根引用链**，就会被判定为存活对象；一旦引用链断裂、引用被覆盖或销毁，对象即刻沦为垃圾，核心分为引用切断、作用域销毁、逻辑废弃三类场景。

### 托管垃圾核心产生场景

1. **引用变量重新赋值**

   原有引用类型变量指向堆中对象，后续被 `null` 或新对象覆盖，旧对象失去所有外部引用，直接变为垃圾。频繁创建短周期临时引用对象。

2. **局部变量生命周期结束**

   方法、循环、代码块内声明的局部引用类型变量，存储于线程栈。当代码执行走出当前作用域，栈上局部引用自动销毁，仅保留在托管堆的对象失去引用支撑，自动转化为垃圾。

3. **集合容器移除 / 清空元素**

   List、Dictionary、Array 等集合容器存储引用类型对象时，容器持有对象有效引用。当执行移除元素、清空集合、容器销毁操作后，内部对象引用被清除，堆内对象无其他引用绑定，形成批量垃圾。

4. **临时对象与装箱拆箱操作**

   字符串拼接、隐式类型转换、函数传参等操作会频繁生成**临时托管对象**，方法执行结束后临时对象立即失效；值类型发生装箱时，会在堆上创建包装对象，使用完毕后无持久引用，持续产生碎片化垃圾。

5. **层级对象销毁与资源解绑**

   Unity 场景中，物体脚本组件、子对象、事件订阅、委托回调等存在双向引用。当物体销毁、组件禁用、事件未手动取消订阅时，多余引用残留或引用断裂，会产生孤立的托管垃圾对象，甚至引发内存泄漏式垃圾堆积。

6. **静态引用不合理持有**

   静态变量生命周期贯穿程序全程，若静态集合、静态全局变量长期临时引用短期业务对象，业务逻辑结束后未手动置空引用，会导致对象无法被 GC 回收，形成常驻无效垃圾占用。

## GC 核心基础定义与职责边界

### 核心定义
GC（Garbage Collection，垃圾回收）是Unity Mono/IL2CPP 托管运行时内置的**自动内存管理机制**，核心负责**托管堆内存**的分配、存活对象追踪、垃圾内存回收与内存整理，无需开发者手动申请/释放托管内存，从根本上避免了手动内存管理的内存泄漏、野指针等问题。

### 职责边界：托管内存 vs 非托管内存
Unity 内存分为两大区域，GC 仅负责托管内存的管理，二者边界明确：
- **托管内存**：由C#脚本通过**`new`创建的引用类型对象**、**装箱操作产生的对象**、**字符串**、**数组**等，由Mono/IL2CPP运行时托管堆分配，完全受GC管控，生命周期由GC自动管理。
- **非托管内存**：Unity引擎底层C++创建的资源对象（纹理、网格、材质、Shader、动画Clip等）、原生插件分配的内存、手动通过`Marshal`类分配的非托管内存，**不受GC管控**，必须由开发者手动调用对应接口释放，仅其对应的C#包装类（如`Texture2D`）的托管实例受GC管理。

### 托管堆核心基础
**托管堆**是GC管理的逻辑连续内存地址空间，用于存放所有托管引用类型对象，核心特点：

- **引用类型对象的实例始终分配在托管堆**。
- 值类型默认分配在线程栈，仅装箱时会被包装为对象分配到托管堆。
- 托管堆采用**段式内存管理**，由多个内存段（Segment）组成，每个段的大小由运行平台、CPU架构决定，当现有段无法满足分配需求时，运行时会向操作系统申请新的内存段扩容托管堆。
- 托管堆的内存分配效率远高于非托管堆：新对象默认分配在托管堆的当前分配指针位置，仅需移动指针即可完成分配，无需遍历空闲列表。

## Unity GC 核心实现与运行模式
### 核心回收器实现
Unity 全平台默认使用 **Boehm–Demers–Weiser (BDW) GC**，这是一款通用的、**保守式**、**支持增量**执行、标记-清除-压缩的垃圾回收器，也是Unity至今的主流GC实现。
- **保守式GC核心特性**：GC无法100%精确区分内存中的值是对象引用还是普通数值，会将所有可能指向托管堆的数值都视为有效引用，避免误回收存活对象。代价是可能出现**误标记**（将非引用数值当成对象引用，导致本应被回收的对象被标记为存活），同时限制了压缩阶段的部分优化能力。
- Unity 2021及以上版本在部分桌面平台实验性支持了**ZGC（零延迟GC）**，但主流移动端、主机平台仍以BDW GC为默认实现。

### 核心运行模式
Unity BDW GC 提供两种核心运行模式，直接决定GC的执行方式与主线程阻塞表现：
#### 非增量模式（Stop-The-World，STW 全阻塞模式）
- 这是Unity早期版本的默认模式，GC的**完整标记-清除-压缩流程全程在主线程同步阻塞执行**，执行期间主线程所有逻辑（渲染、生命周期、物理、UI、输入）完全暂停，直到GC全流程执行完毕。
- 特点：GC总耗时最短，但单次阻塞时间极长，复杂场景下全堆GC（Full GC）可造成数百毫秒的主线程冻结，直接表现为严重卡顿、帧率暴跌。

#### 增量模式（Incremental GC，Unity 5.6+ 支持，现代Unity默认开启）
- 核心设计：将GC的完整流程（尤其是耗时最长的标记阶段、压缩阶段）**拆分为多个小的时间片，分散到多个游戏帧中分步执行**，把单次长时长的STW阻塞，拆解为多次短时长的小阻塞，大幅降低单帧卡顿峰值，保证帧率平滑。
- 核心支撑：**写屏障（Write Barrier）机制**。增量标记过程中，主线程仍在正常运行，可能随时修改对象的引用关系，导致已完成标记的对象出现引用变更，引发**漏标问题**（存活对象未被标记，被误回收）。写屏障会在所有对象引用修改的位置插入钩子，记录引用变更的对象，在后续的增量标记步骤中重新扫描这些对象，保证标记结果的准确性，是增量GC可正常运行的核心底层机制。
- 特点：GC总耗时略高于非增量模式，但单帧主线程阻塞时间被严格控制，帧率稳定性大幅提升，是现代Unity项目的默认首选模式。

## GC 完整工作流程
Unity BDW GC 一次完整的回收流程，分为**5个核心阶段**，全流程严格按顺序执行：

### 阶段1：标记阶段（Mark）
标记阶段是GC最核心、耗时占比最高的阶段，核心目标是**识别出托管堆中所有仍在被使用的存活对象，区分出可回收的垃圾对象**。
1. **标记起点：GC 根引用（GC Roots）**
   GC 根引用是标记的起点，是堆外指向堆内对象的有效引用，被根引用直接/间接指向的对象，判定为存活对象。Unity中完整的GC根引用包括：
   - 静态字段、静态属性：全局静态变量的生命周期与应用程序一致，始终为有效根引用。
   - 当前执行栈的局部变量、方法参数：所有正在执行的方法栈帧中的局部变量、入参，正在被线程使用，为有效根引用。
   - CPU寄存器中存放的对象引用：正在被CPU执行的对象引用，为有效根引用。
   - 活跃的`GCHandle`：开发者手动创建的、用于托管/非托管交互的对象句柄，包括正常引用、弱引用、固定引用。
   - Unity引擎内部对象引用：引擎底层C++持有的托管对象引用，如活跃的`MonoBehaviour`/`ScriptableObject`实例、挂载在场景中的物体对应的C#包装类、正在执行的协程引用等。
2. **标记执行流程**
   - 初始化阶段：暂停主线程（STW），初始化标记位图，将所有托管对象默认标记为“不可达（垃圾）”。
   - 根扫描：遍历所有GC根引用，将根引用直接指向的对象标记为“可达（存活）”，加入待扫描队列。
   - 递归遍历：深度优先/广度优先遍历待扫描队列中对象的所有引用字段，将被引用的对象也标记为存活，加入待扫描队列，直到待扫描队列为空。
   - 增量模式下：递归遍历过程被拆分为多个时间片，每个时间片执行一小部分遍历，执行完后恢复主线程运行，下一帧继续执行剩余的遍历，直到全量标记完成。
3. **保守式标记的特点**
   由于BDW GC是保守式回收器，标记阶段会将所有可能指向托管堆的数值都视为有效引用，避免误回收，但可能导致部分无引用的对象被误标记为存活，无法被回收，造成隐性的内存浪费。

### 阶段2：终结器处理阶段（Finalizer Processing）
终结器（C#中为析构函数`~ClassName()`）是.NET提供的、用于对象回收前执行非托管资源清理的机制，该阶段是GC流程中独立的关键环节，直接影响对象的回收生命周期。
1. **核心执行流程**
   - 标记阶段完成后，GC会筛选出所有**带有终结器、且未被标记为存活的对象**，这些对象不会被立即回收，而是被移入**终结器队列（Finalizer Queue）**。
   - 恢复主线程运行，由运行时专门的**终结器线程**，异步执行队列中所有对象的终结器方法。
   - 执行完终结器的对象，会被移入**f-reachable队列**，等待下一次GC执行时，才会被判定为可回收垃圾。
2. **核心特性**
   - 带有终结器的对象，**至少需要经历2次GC才能被完全回收**，第一次GC触发终结器执行，第二次GC才会回收对象内存。
   - 若终结器执行耗时过长、或终结器队列堵塞，会导致对象长期无法被回收，甚至晋升到高代，大幅增加GC开销。
   - 若终结器执行中重新为对象添加了有效引用，会导致对象“复活”，重新被标记为存活，无法被回收。

### 阶段3：清除阶段（Sweep）
清除阶段的核心目标是**回收所有未被标记为存活的垃圾对象占用的内存，将其重新纳入可用内存管理**。
1. **核心执行流程**
   - 逐段扫描托管堆的所有内存段，遍历每个内存块。
   - 对于未被标记为存活的垃圾对象：释放其占用的内存，将该内存块加入**空闲内存链表（Free List）**，标记为可分配状态。
   - 对于存活对象：保留其内存占用，重置其标记位，为下一次GC做准备。
2. **核心特点**
   - 清除阶段不会移动存活对象的内存地址，因此执行后会在托管堆中产生大量不连续的空闲内存块，即**内存碎片**。
   - 增量模式下，清除阶段也可拆分为多帧分步执行，进一步降低单帧STW时间。
   - 清除阶段仅处理无终结器、或终结器已执行完毕的垃圾对象，终结器队列中的对象不会被清除。

### 阶段4：压缩阶段（Compact）
压缩阶段的核心目标是**解决内存碎片问题，整理托管堆内存，提升后续内存分配效率**。
1. **核心执行流程**
   - 扫描托管堆中的所有存活对象，将其移动到托管堆的连续内存区域，紧密排列，消除对象之间的空闲内存碎片。
   - 移动完成后，将所有分散的空闲内存块合并为一个连续的大内存块，更新空闲内存链表。
   - 增量模式下，压缩操作会被拆分为多个小批次，分散到多帧执行，避免单次压缩造成的长时间STW。
2. **核心限制与特点**
   - 压缩阶段必须修改所有存活对象的内存地址，因此需要**修正所有指向这些对象的引用**（包括GC根引用、对象内部的引用字段），保证引用指向新的内存地址，该过程必须在STW下执行。
   - **固定对象（Pinned Object）** 无法被移动：通过`fixed`关键字、`GCHandle.Alloc(..., GCHandleType.Pinned)`固定的对象，会被锁定在原内存地址，压缩阶段无法移动，会导致其周围的内存碎片无法被合并，是托管堆内存碎片的核心成因之一。
   - 压缩阶段不会每次GC都触发：仅当托管堆内存碎片率达到阈值、或空闲内存块无法满足大对象分配需求时，GC才会执行压缩阶段，减少不必要的性能开销。

### 阶段5：引用修正与收尾阶段
压缩阶段完成后，GC会执行最终的收尾工作：
1. 修正所有存活对象的引用地址，包括GC根引用、对象内部的引用字段、CPU寄存器中的引用、活跃的`GCHandle`，确保所有引用都指向对象移动后的新地址。
2. 更新托管堆的分配指针，将其指向连续内存区域的末尾，后续新对象可直接在该位置分配。
3. 重置GC的内部状态、标记位图，恢复主线程的完全运行，本次GC流程结束。

## 核心GC算法深度解析
### 标记-清除-压缩算法
这是Unity BDW GC的核心基础算法，是标记-清除算法的增强版，完整解决了基础算法的内存碎片问题。
#### 基础标记-清除算法
- 核心逻辑：分为独立的**标记**与**清除**两个阶段，无压缩步骤。
- 优点：实现简单，存活对象无需移动，单次回收的基础开销低。
- 致命缺点：清除后会产生大量内存碎片，随着运行时间增加，碎片率持续升高，最终导致明明有足够的总空闲内存，却没有连续的大块内存满足大对象分配，触发频繁的Full GC甚至托管堆扩容，内存利用率极低。
- Unity中的应用：仅在早期Unity版本、非增量模式下的小范围0代GC中使用，现代Unity已极少单独使用该算法。

#### 标记-清除-压缩算法
- 核心逻辑：在标记-清除的基础上，新增**压缩阶段**，通过移动存活对象、合并空闲内存，彻底解决内存碎片问题。
- 优点：内存利用率极高，几乎无内存碎片，后续新对象分配效率极高，可有效减少托管堆的频繁扩容。
- 缺点：压缩阶段需要移动对象、修正所有引用，额外增加了GC的性能开销，且必须在STW下执行引用修正步骤。
- Unity中的应用：现代Unity默认的全量GC、Full GC均采用该算法，增量模式下会拆分压缩步骤降低单帧开销。

### 分代回收算法（Generational GC）
分代回收是基于**弱代假说**设计的优化算法，弱代假说包含两个核心经验规律：
1. 绝大多数对象都是短生命周期的，创建后很快就会变成垃圾；
2. 存活时间越长的对象，越不容易变成垃圾。

Unity BDW GC 基于该假说实现了分代回收机制，将托管堆中的对象按生命周期划分为**0代、1代、2代**三个代际，通过限制每次GC的扫描范围，大幅降低GC的性能开销。

#### 各代际的核心定义与特性
| 代际 | 核心定义 | 堆空间大小 | GC扫描速度 | 触发频率 | 核心特点 |
|------|----------|------------|------------|----------|----------|
| 0代  | 新创建的、从未经历过GC回收的短生命周期托管对象 | 最小 | 极快 | 最高 | 绝大多数新对象都分配在0代，绝大多数0代对象都会在本次GC中被回收，仅扫描0代对象，开销极低 |
| 1代  | 在0代GC中存活下来、经历过1次GC回收的中等生命周期对象 | 中等 | 中等 | 中等 | 0代与2代之间的缓冲带，减少短生命周期对象直接晋升到2代的概率，仅当0代GC后仍无法满足分配需求时，才会触发1代GC，扫描0代+1代对象 |
| 2代  | 在1代GC中存活下来、经历过至少2次GC回收的长生命周期对象 | 最大 | 极慢 | 最低 | 存放单例、全局缓存、常驻场景对象等长期存活的对象，触发2代GC时会扫描全堆所有代际的对象（Full GC），开销最高，耗时最长 |

#### 代晋升规则
对象的代际并非固定不变，会根据存活情况向上晋升，核心规则：
1. 0代对象在0代GC中被标记为存活，会直接晋升到1代；
2. 1代对象在1代GC中被标记为存活，会直接晋升到2代；
3. 2代是最高代际，晋升到2代的对象，会一直停留在2代，直到被回收；
4. 带有终结器的对象，若第一次GC未被回收，会直接晋升到更高代际，大幅延长其生命周期。

#### 分代回收的核心执行逻辑
- 优先触发0代GC：当新对象分配时，优先尝试在0代分配，若0代空间不足，仅触发0代GC，只扫描0代对象，回收0代垃圾，开销极低。
- 逐级触发高代GC：若0代GC回收后，仍无法满足分配需求，会触发1代GC，扫描0代+1代对象；若1代GC后仍不足，才会触发2代Full GC，扫描全堆所有对象。
- 高代GC会自动触发低代GC：触发1代GC时，会同时执行0代GC；触发2代Full GC时，会同时执行0代+1代GC，保证全堆垃圾都被回收。
- 核心优势：绝大多数GC都是低开销的0代GC，仅在必要时才触发高开销的全堆GC，从整体上大幅降低了GC的平均性能开销，减少了主线程阻塞时间。

## GC 触发机制全解析
GC的触发分为**隐式自动触发**与**显式手动触发**两大类，所有触发最终都会回归到托管堆内存分配的核心逻辑，完整触发类型与底层原理如下：

| 触发类型 | 触发时机 | 底层原理 | 代际范围 | 核心特点 |
|----------|----------|----------|----------|----------|
| **分配失败触发** | C#脚本`new`引用类型对象、装箱操作、字符串拼接、数组创建等托管内存分配操作时，当前代的空闲内存无法满足分配需求 | 托管堆分配器在分配内存时，先检查当前代的剩余空间，若无法满足分配，会立即触发对应代的GC，尝试回收内存完成分配 | 优先0代，逐级向上 | 项目运行中最频繁的触发方式，由运行时自动隐式触发，触发时机不可精确预知，绝大多数为低开销的0代GC，频繁触发仍会造成帧率波动 |
| **手动调用触发（显式）** | 代码主动执行`GC.Collect()`系列接口：<br>1. `GC.Collect()`：无参重载<br>2. `GC.Collect(int generation)`：指定代际<br>3. `GC.Collect(GCCollectionMode mode)`：指定回收模式 | 强制运行时立即执行对应代际的垃圾回收，无视当前内存分配状态，同步执行完整的GC流程，直到回收完成 | 无参默认触发2代Full GC；可指定代际 | 会强制阻塞主线程直到回收完成，频繁调用极易造成严重卡顿，仅建议在切场景、加载完毕等非性能关键节点使用 |
| **场景切换触发（隐式）** | 使用`SceneManager.LoadScene`/`LoadSceneAsync`同步/异步加载/切换场景时 | Unity引擎默认会在场景卸载完成后，自动执行`Resources.UnloadUnusedAssets()`卸载未使用资源，同时触发全堆2代Full GC，清理场景卸载产生的大量垃圾对象 | 2代Full GC | 引擎自动触发，属于性能可接受的回收时机，可通过`UnityEngine.Scripting.GarbageCollector.GCMode`禁用自动GC，手动控制回收时机 |
| **资源卸载触发（隐式/显式）** | 1. 手动调用`Resources.UnloadUnusedAssets()`<br>2. 调用`AssetBundle.Unload(true)`完全卸载AB包<br>3. 调用`Object.DestroyImmediate`批量销毁资源 | 资源卸载后，大量资源对应的C#托管包装类失去引用，变成垃圾对象，运行时会自动触发GC，回收这些对象占用的托管内存 | 通常为2代Full GC | 必定伴随GC执行，多用于切场景、资源池释放后，降低内存占用，可手动控制触发时机 |
| **系统内存压力触发（隐式）** | 1. 设备系统可用内存过低<br>2. 托管堆持续扩容达到平台设定的阈值<br>3. 系统触发低内存回调（如Android的Low Memory、iOS的Memory Warning） | 平台运行时监听到系统内存压力，会强制触发全堆Full GC，尽可能回收内存，避免应用被系统强制杀死 | 2代Full GC | 不可控，回收耗时通常更长，不同平台、不同设备的触发策略差异极大，移动端触发频率远高于PC端 |
| **应用退出/暂停触发（隐式）** | 应用退到后台、暂停、退出时 | Unity引擎会在应用暂停/退出时，自动触发全堆GC与资源卸载，释放不必要的内存，避免后台占用过高被系统杀死 | 2代Full GC | 对前台运行的帧率无影响，属于系统级的安全回收 |

### 补充：托管堆扩容与GC触发的关联
当所有代际的GC执行完成后，托管堆的总空闲内存仍无法满足当前的内存分配需求时，Mono/IL2CPP运行时会向操作系统申请新的内存段，**扩容托管堆**。
- 托管堆扩容的开销远高于GC，会造成明显的主线程阻塞，同时会增加后续Full GC的扫描范围与耗时。
- 托管堆扩容后，只会在应用退出时才会将内存释放给操作系统，运行时不会主动缩小托管堆的总大小，仅会回收内部的空闲内存。

## Mono vs IL2CPP 运行时的GC实现差异
Unity的两种脚本运行时，均基于BDW GC实现，但在底层原理、执行效率、标记精度上有本质差异，直接影响GC的性能表现：

| 对比维度 | Mono 运行时 | IL2CPP 运行时 |
|----------|-------------|---------------|
| GC标记精度 | 完全保守式GC，无法精确区分引用与数值，易出现误标记，标记效率低 | 混合式GC，默认启用**部分精确式标记**：IL2CPP会在编译时生成完整的对象元数据，明确告知GC对象中哪些字段是引用类型，哪些是值类型，仅对栈上的变量采用保守式标记，标记精度大幅提升，误标记概率极低 |
| 标记阶段效率 | 低：保守式标记需要扫描所有可能的内存地址，遍历范围大，耗时更长 | 高：精确式标记仅需扫描元数据标记的引用字段，遍历范围大幅缩小，标记耗时显著降低，同场景下GC总耗时比Mono低30%~50% |
| 增量GC支持 | 支持，但优化有限，单帧STW时间控制较弱 | 深度优化，增量标记的拆分粒度更细，写屏障机制更高效，单帧STW时间控制更严格，帧率稳定性更好 |
| 终结器处理 | 终结器线程优先级低，易出现队列堵塞，对象回收延迟高 | 终结器线程调度优化，执行效率更高，回收延迟更低 |
| 托管堆布局 | 段式管理，段大小固定，扩容策略保守，易出现频繁扩容 | 段式管理，段大小根据平台动态调整，扩容策略更激进，减少频繁扩容的开销，内存利用率更高 |
| 平台兼容性 | 全平台支持，仅在部分老平台使用 | 现代Unity默认运行时，全平台支持，是主机、移动端平台的唯一可选运行时 |

## GC 核心关联机制原理补充
### 写屏障（Write Barrier）
写屏障是增量GC、分代GC的核心底层支撑机制，是一段在**对象引用被修改时自动执行的钩子代码**。
- 核心作用1（增量GC）：记录增量标记过程中被修改的对象引用，避免漏标存活对象，保证增量标记的结果准确。
- 核心作用2（分代GC）：记录老年代对象对新生代对象的引用，避免0代GC时需要扫描整个2代堆，大幅降低0代GC的扫描开销。
- 执行时机：所有对对象引用字段的赋值操作，都会自动触发写屏障，记录引用变更信息。

### GCHandle 与 对象固定（Pinning）
`GCHandle`是.NET提供的、用于从非托管代码访问托管对象的句柄，核心分为4种类型，直接影响GC的行为：
- `GCHandleType.Normal`：正常引用句柄，会将对象标记为GC根引用，保证对象不会被GC回收，可从非托管代码访问。
- `GCHandleType.Weak`：弱引用句柄，不会将对象标记为存活，不影响GC回收对象，对象被回收后句柄自动失效。
- `GCHandleType.Pinned`：固定引用句柄，不仅会保证对象不被回收，还会**将对象固定在托管堆的原内存地址，GC压缩阶段无法移动该对象**，常用于非托管代码直接访问托管数组的内存地址。
- `GCHandleType.WeakTrackResurrection`：长弱引用句柄，可追踪对象终结器执行后的复活状态。

### 弱引用（WeakReference）
弱引用是一种不会阻止GC回收对象的引用类型，核心分为两种：
- 短弱引用：对象被GC标记为垃圾后，引用立即失效，不会追踪对象的终结器执行与复活。
- 长弱引用：对象终结器执行完毕后，引用才会失效，可追踪对象的复活状态。
- 核心原理：弱引用指向的对象，不会被GC标记为存活，不影响GC的回收逻辑，适用于缓存大对象、非关键对象，在内存不足时可被GC自动回收，平衡内存占用与访问效率。

### 内存碎片的成因与GC的处理
托管堆内存碎片分为两种类型，GC的处理方式不同：
1. **释放型碎片**：清除阶段回收垃圾对象后，产生的分散的小空闲内存块，GC可通过**压缩阶段**移动存活对象，合并这些空闲块，彻底解决。
2. **固定型碎片**：固定对象（Pinned Object）周围无法被合并的空闲内存块，由于固定对象无法被移动，GC压缩阶段无法合并其周围的空闲内存，只能通过减少固定对象的使用、缩短固定对象的生命周期来缓解，无法通过GC完全消除。

## GC 与 Unity 主线程的交互原理
### 主线程与STW的核心关系
Unity引擎的核心逻辑，包括渲染循环、`MonoBehaviour`全生命周期、物理更新、UI布局与渲染、输入事件响应、动画更新，**全部运行在主线程**。而BDW GC的核心执行步骤，必须在主线程的STW（Stop-The-World）状态下执行，这是GC卡顿的本质原因。
- **STW的核心定义**：GC执行时，会暂停主线程的所有托管代码执行，同时暂停所有子线程的托管代码访问，保证对象引用关系不会在GC执行过程中被修改，确保标记、清除、压缩、引用修正的结果准确。
- **必须STW的阶段**：标记阶段的根扫描、引用修正阶段、压缩阶段的对象移动与地址更新，这些步骤必须在完全STW的状态下执行，否则会出现引用错乱、对象误回收、内存崩溃等致命问题。
- **可增量执行的阶段**：标记阶段的递归遍历、清除阶段的内存扫描与回收，这些步骤可通过增量模式拆分为多个小的STW时间片，分散到多帧执行，降低单帧阻塞时间。

### 常见误区澄清
1. **误区1：IL2CPP可以让GC在子线程执行，不阻塞主线程**
   澄清：IL2CPP仅优化了GC的执行效率与标记精度，GC的核心STW阶段仍必须在主线程执行，无法完全脱离主线程，仅能缩短阻塞时间，无法从根本上消除卡顿。

2. **误区2：协程/异步任务可以避免GC触发与主线程阻塞**
   澄清：协程、`async/await`异步任务，本质仍是在主线程执行，只要涉及托管内存分配，就会触发GC，GC执行时仍会阻塞主线程，无法从根本上避免GC卡顿，仅能将内存分配分散到非关键帧，减少峰值卡顿。

3. **误区3：子线程的托管对象分配不会触发GC**
   澄清：子线程中执行`new`引用类型、装箱等操作，同样会在托管堆分配内存，分配失败时同样会触发GC，且GC触发时会暂停所有线程（包括子线程），同时阻塞主线程，仅能避免分配逻辑占用主线程时间，无法避免GC的主线程阻塞。

## GC 优化
### GC 优化核心手段
#### 减少堆分配
- **避免帧内高频分配**：禁止在 `Update`、`LateUpdate`、`FixedUpdate` 等每帧执行的方法中 `new` 引用类型对象（如自定义类、`List<T>`、数组等），将其移至 `Awake`/`Start` 初始化。
- **预分配与复用集合**：初始化集合时显式设置 `Capacity`，避免运行时动态扩容；使用后调用 `Clear()` 清空内容而非重新 `new`，实现复用。
  ```csharp
  // 错误示例：Update 中动态扩容
  void Update() {
      List<int> tempList = new List<int>(); // 每帧分配新 List
      tempList.Add(1);
  }
  
  // 正确示例：预分配 + 复用
  private List<int> reusableList = new List<int>(100); // 初始化时指定容量
  void Update() {
      reusableList.Clear(); // 清空内容，不释放内存
      reusableList.Add(1);
  }
  ```
- **使用 `ArrayPool<T>` 复用数组**：对于临时数组，通过 `ArrayPool<T>.Shared` 租借/归还，避免频繁分配与释放。
  ```csharp
  using System.Buffers;
  void ProcessData() {
      int[] tempArray = ArrayPool<int>.Shared.Rent(100); // 租借数组
      try {
          // 使用 tempArray（注意实际长度可能大于请求长度）
      }
      finally {
          ArrayPool<int>.Shared.Return(tempArray); // 归还数组
      }
  }
  ```

#### 避免装箱拆箱
- **优先使用泛型集合**：用 `List<T>`、`Dictionary<TKey, TValue>` 替代 `ArrayList`、`Hashtable`，避免值类型存入非泛型集合时的装箱。
  ```csharp
  // 错误示例：ArrayList 装箱
  ArrayList badList = new ArrayList();
  badList.Add(123); // int 装箱为 object
  
  // 正确示例：泛型集合无装箱
  List<int> goodList = new List<int>();
  goodList.Add(123); // 直接存储 int
  ```
- **避免值类型转接口**：若结构体实现接口，调用接口方法时会装箱，可通过泛型约束避免。
  ```csharp
  // 避免：struct 转接口装箱
  interface IProcess { void Execute(); }
  struct MyStruct : IProcess { public void Execute() { } }
  void BadMethod(IProcess p) { p.Execute(); } // 调用时装箱
  
  // 推荐：泛型约束无装箱
  void GoodMethod<T>(T p) where T : IProcess { p.Execute(); }
  ```
- **避免 `params` 参数**：`params object[]` 会隐式分配数组，值类型传入还会装箱，改用重载或显式数组传递。

#### 字符串优化
- **禁止高频 `+` 拼接**：字符串是不可变类型，每次 `+` 都会生成新字符串，改用 `StringBuilder` 并预分配容量。
  ```csharp
  // 错误示例：每帧多次字符串分配
  void Update() {
      string log = "Frame: " + Time.frameCount + ", Time: " + Time.time; // 多次分配
  }
  
  // 正确示例：StringBuilder 预分配 + 复用
  private StringBuilder sb = new StringBuilder(256); // 预分配容量
  void Update() {
      sb.Clear();
      sb.Append("Frame: ").Append(Time.frameCount).Append(", Time: ").Append(Time.time);
      string result = sb.ToString(); // 仅一次分配
  }
  ```
- **缓存常量字符串**：用 `string.Intern` 缓存高频使用的字符串，或用静态字段存储，避免运行时重复生成。
- **使用 `Span<char>` 避免分配**：Unity 2021+ 支持 `Span<char>`，可在不分配新字符串的情况下截取、修改字符串片段。

#### 缓存与复用
- **缓存组件与 API 结果**：在 `Awake`/`Start` 中缓存 `GetComponent<T>`、`Camera.main` 等结果，避免每帧调用。
  ```csharp
  private Collider myCollider;
  private Camera mainCamera;
  void Awake() {
      myCollider = GetComponent<Collider>(); // 缓存组件
      mainCamera = Camera.main; // 缓存 Camera
  }
  ```
- **对象池复用动态对象**：对频繁创建/销毁的对象（如子弹、特效、UI 元素）使用对象池，避免 `Instantiate`/`Destroy` 带来的 GC 与性能开销。
  ```csharp
  // 简单对象池实现
  public class ObjectPool : MonoBehaviour {
      public GameObject prefab;
      private Queue<GameObject> pool = new Queue<GameObject>();
  
      public GameObject Get() {
          if (pool.Count > 0) {
              GameObject obj = pool.Dequeue();
              obj.SetActive(true);
              return obj;
          }
          return Instantiate(prefab);
      }
  
      public void Return(GameObject obj) {
          obj.SetActive(false);
          pool.Enqueue(obj);
      }
  }
  ```
- **复用值类型临时变量**：将 `Vector3`、`Quaternion` 等值类型临时变量声明为类成员，避免每帧在栈上重复分配（虽无 GC，但可提升缓存命中率）。

#### 闭包与 LINQ 优化
- **避免帧内闭包**：闭包会捕获外部变量并生成隐藏的引用类型“捕获类”，造成堆分配。若必须使用，将外部变量拷贝为局部变量。
  ```csharp
  // 错误示例：闭包捕获循环变量，每帧分配捕获类
  void BadLoop() {
      for (int i = 0; i < 10; i++) {
          button.onClick.AddListener(() => Debug.Log(i)); // 捕获 i，分配堆内存
      }
  }
  
  // 推荐：局部变量拷贝，减少分配
  void GoodLoop() {
      for (int i = 0; i < 10; i++) {
          int temp = i; // 拷贝到局部变量
          button.onClick.AddListener(() => Debug.Log(temp)); // 捕获 temp，仍有分配但更可控
      }
  }
  
  // 最佳：避免闭包，用方法替代
  void OnButtonClick(int value) => Debug.Log(value);
  ```
- **避免 Update 中使用 LINQ**：LINQ 会生成临时 `IEnumerable` 与迭代器对象，造成堆分配，改用 `for` 循环替代。
  ```csharp
  // 错误示例：LINQ 分配临时对象
  void Update() {
      var result = myList.Where(x => x > 0).ToList(); // 分配 IEnumerable + List
  }
  
  // 正确示例：for 循环无分配
  private List<int> resultList = new List<int>();
  void Update() {
      resultList.Clear();
      for (int i = 0; i < myList.Count; i++) {
          if (myList[i] > 0) resultList.Add(myList[i]);
      }
  }
  ```

#### 结构体优先
- **轻量数据用 `struct`**：对于小数据（如 2-3 个字段的坐标、状态）用 `struct`，分配在栈或内联在堆中，无 GC 压力。
- **大 `struct` 用 `in`/`ref` 传递**：避免大结构体拷贝开销，通过 `in`（只读引用）或 `ref` 传递。
  ```csharp
  // 大结构体示例
  public struct LargeStruct {
      public int a, b, c, d, e, f, g, h;
  }
  
  // 避免：值传递拷贝整个结构体
  void BadMethod(LargeStruct s) { }
  
  // 推荐：in 只读引用传递，无拷贝
  void GoodMethod(in LargeStruct s) { }
  ```


### 常见 GC 分配点
1. **引用类型实例化**：`new Class()`、`new List<T>()`、`new T[]` 等。
2. **字符串操作**：`+` 拼接、`Substring`、`ToUpper`/`ToLower`、`string.Format`（非缓存时）。
3. **值类型装箱**：`int`→`object`、`struct`→接口、`params object[]` 传值类型、`Debug.Log("Num: " + 1)`。
4. **闭包与迭代器**：lambda 捕获外部变量、`IEnumerator` 迭代器、LINQ 查询。
5. **协程对象**：`new WaitForSeconds(1f)`、`new WaitForFixedUpdate()`（应缓存）、`yield return null` 无分配，但 `yield return new XXX()` 有分配。
6. **Unity API 隐式分配**：
   - `GetComponents<T>()`、`FindObjectsOfType<T>()`：每次返回新数组。
   - `renderer.material`：创建新的 `Material` 实例（用 `sharedMaterial` 或 `MaterialPropertyBlock` 替代）。
   - `Sprite.Create()`：每次生成新 `Sprite`。
7. **委托与事件**：`myEvent += MyMethod` 会创建新的委托实例（避免频繁注册/注销）。
8. **非泛型集合与 `foreach`**：`ArrayList` 存值类型装箱、`foreach` 遍历非泛型集合分配枚举器。


### Unity GC 陷阱
1. **协程 `yield` 对象**：即使是 `WaitForEndOfFrame`，每次 `new` 也会分配，需缓存为静态字段。
   ```csharp
   // 缓存示例
   private static WaitForEndOfFrame waitForEndOfFrame = new WaitForEndOfFrame();
   IEnumerator MyCoroutine() {
       yield return waitForEndOfFrame; // 复用，无分配
   }
   ```
2. **`GetComponent` 无 GC 但高频调用耗性能**：虽无堆分配，但每帧调用仍有 CPU 开销，务必缓存。
3. **`UnityWebRequest` 未释放**：需用 `using` 包裹或手动调用 `Dispose()`，否则会造成托管+原生内存双重泄漏。
   ```csharp
   using (UnityWebRequest request = UnityWebRequest.Get(url)) {
       yield return request.SendWebRequest();
       // 处理结果
   } // 自动释放，无泄漏
   ```
4. **`MaterialPropertyBlock` 替代材质实例**：修改材质属性时，用 `MaterialPropertyBlock` 避免创建新 `Material`。
   ```csharp
   private MaterialPropertyBlock mpb = new MaterialPropertyBlock();
   void Update() {
       mpb.SetFloat("_Speed", Time.time);
       renderer.SetPropertyBlock(mpb); // 无材质分配
   }
   ```
5. **`Debug.Log` 的隐式分配**：即使字符串不拼接，`Debug.Log` 本身在某些平台也会有少量分配，发布版本可通过宏禁用。


### GC 优化工具
#### Profiler CPU 模块
- **使用步骤**：`Window > Analysis > Profiler`，选择 **CPU** 模块，勾选 **GC Alloc** 列。
- **定位方法**：运行游戏，观察哪一帧的 **GC Alloc** 值过高，点击展开函数调用树，找到具体分配代码（橙色标记为 GC 触发点）。

#### Memory Profiler
- **核心功能**：`Window > Analysis > Memory Profiler`，点击 **Capture** 抓取托管堆快照，对比两个快照可查看对象增长情况，分析引用链定位内存泄漏。
- **适用场景**：排查“内存持续增长但无明显 GC”的泄漏问题。

#### Deep Profile

- **使用限制**：仅编辑器可用，会大幅降低运行性能，适合小范围代码深度分析。
- **功能**：追踪所有函数调用的 GC 分配与 CPU 耗时，精准定位细粒度分配点。

### 简易 GC 检测代码
- 快速检测帧内分配，无需打开 Profiler：
  ```csharp
  private long lastMemory = 0;
  void Update() {
      long currentMemory = GC.GetTotalMemory(false);
      if (currentMemory > lastMemory) {
          Debug.Log($"GC Alloc: {currentMemory - lastMemory} bytes");
      }
      lastMemory = currentMemory;
  }
  ```

### GC 优化最佳实践

#### 代码层面
- **循环三禁止**：循环内禁止字符串拼接、禁止 `new` 临时数组、禁止装箱操作。
- **协程对象全缓存**：`WaitForSeconds`、`WaitForFixedUpdate` 等均缓存为静态字段。
- **结构体替代小类**：小于 16 字节的轻量数据优先用 `struct`，超过 16 字节考虑 `in`/`ref` 传递。
- **闭包仅在初始化用**：避免 `Update` 中使用闭包，必要时用局部变量拷贝或方法替代。
- **非必要不手动 `GC.Collect()`**：强制全堆 GC 会造成严重卡顿，仅在切场景、加载完毕等非关键节点使用。

#### Unity 引擎层面
- **发布用 IL2CPP**：IL2CPP 的 GC 标记精度与执行效率远高于 Mono，且支持更激进的代码裁剪。
- **启用增量 GC**：`Player Settings > Other Settings > Garbage Collector` 选择 **Incremental**，将 GC 拆分为多帧执行，降低单帧卡顿。
- **避免 2 代对象频繁增长**：大对象（如 > 85000 字节的数组）会直接分配到 2 代，尽量复用大对象，避免频繁创建。
- **使用 `NativeArray` 与 `Job System`**：Unity 2018+ 支持 `NativeArray<T>`，分配在非托管内存，无 GC 压力，配合 Job System 可进一步提升性能。
  
  ```csharp
  using Unity.Collections;
  using Unity.Jobs;
  
  // 无 GC 的 Job 示例
  public struct ProcessJob : IJob {
      public NativeArray<int> data;
      public void Execute() {
          for (int i = 0; i < data.Length; i++) {
              data[i] *= 2;
          }
      }
  }
  
  // 使用
  void Start() {
      NativeArray<int> array = new NativeArray<int>(1000, Allocator.TempJob);
      ProcessJob job = new ProcessJob { data = array };
      JobHandle handle = job.Schedule();
      handle.Complete(); // 等待 Job 完成
      array.Dispose(); // 释放非托管内存
  }
  ```

#### 内存管理层面
- **对象池覆盖高频对象**：子弹、特效、UI 列表项等动态对象 100% 使用对象池。
- **资源卸载后手动 GC**：调用 `Resources.UnloadUnusedAssets()` 后，可在非关键帧手动调用 `GC.Collect()` 清理托管内存。
- **托管堆扩容预警**：通过 `GC.GetTotalMemory(false)` 监控托管堆大小，若持续增长，优先排查内存泄漏与不必要的分配。


### 优化效果验证
- **Profiler 验证**：优化后，CPU 模块的 **`GC Alloc`** 列每帧分配应控制在 0-100 字节以内（理想情况为 0）。
- **帧率验证**：观察帧率曲线，橙色 GC 标记的出现频率与持续时间应显著降低。
- **内存验证**：Memory Profiler 中托管堆大小应稳定，无持续增长的异常对象。
