面向对象

面向对象编程（Object-Oriented Programming，OOP）是一种以「对象」为核心的编程思想，把现实世界中的事物抽象成程序中的「对象」，通过封装、继承、多态三大特性，让代码更易复用、扩展和维护。

核心逻辑：将现实世界的事物拆解为「特征」和「行为」，对应程序中的「属性」和「方法」，通过类的模板化定义，批量创建具有共性的对象，实现代码的模块化、结构化管理。

OOP 核心基础概念

类（Class）

  • 定义：对象的模板 / 蓝图，描述一类对象共有的属性和行为，是对同类事物的抽象提炼
  • 本质：一种自定义的数据类型，整合了数据（属性/字段）和操作数据的行为（方法）
  • 作用：规范同类对象的结构，避免重复定义，为创建对象提供统一标准
  • 语法：
    • C#：class 类名 { }（默认 internal，Unity 中脚本类需继承 MonoBehaviour 时特殊处理）；
    • C++：class 类名 { };（支持 final 修饰类，禁止继承）
  • 特点：不占用实例内存空间，仅作为模板存在，无法直接使用，需通过实例化生成对象后使用
  • 语言差异：
    • C++：类默认访问权限为 private，支持类内成员模板、内联变量（C++ 特性）；
    • C#：类默认访问权限为 internal，Unity 中脚本类若挂载到 GameObject 需为 public，且无无参构造（因 MonoBehaviour 限制）；
    • 类内部成员默认私有规则一致。

对象（Object）

  • 定义：类的实例（具体的个体），是类的具体实现
  • 本质：类的实例化产物，占用内存空间，具备类中定义的所有属性和方法
  • 作用：实际执行程序功能，是程序中具体操作的载体
  • 关系：一个类可以实例化多个对象，多个对象共享类的模板结构，但拥有各自独立的属性值
  • 实例化：
    • C#：
      • 普通类：new 类名() 创建引用类型对象（托管堆）；
      • MonoBehaviour 子类：不能直接 new，需通过 GameObject.AddComponent<类名>() 实例化；
    • C++：
      • 栈实例化：类名 对象名;（自动回收）；
      • 堆实例化：类名* 对象名 = new 类名();（需手动 delete，C++ 推荐 std::unique_ptr/std::shared_ptr 智能指针管理）；
  • 语言差异：
    • C++：原生支持内存手动管理，智能指针（std::unique_ptr/std::shared_ptr）简化堆内存释放，避免内存泄漏；
    • C#：依托托管堆与 GC 自动回收内存，Unity 中需注意「空引用」「GC 卡顿」，可通过对象池减少频繁实例化/销毁。

字段（Field）

  • 定义：类中存储数据的变量，描述对象的特征（如人的姓名、年龄，汽车的颜色、排量）
  • 作用：存储对象的核心数据，是对象特征的直接体现
  • 特点：直接隶属于类或对象，可直接赋值和读取（未封装时），通常建议私有化，通过属性间接访问
  • 分类：
    • 实例字段：属于对象，每个对象有独立值；
    • 静态字段：属于类，所有对象共享同一个值；
  • 语言差异：
    • C++：称字段为成员变量，支持 constexpr（编译期常量）、inline 静态成员变量（C++ 无需类外定义）；
    • C#：严格区分字段与属性，Unity 中字段可通过 [SerializeField] 标记私有字段在 Inspector 面板可视化编辑，[HideInInspector] 隐藏公有字段；支持 readonly 只读字段（构造时赋值）。

属性（Property）

  • 定义：对字段的封装，是字段的访问接口，控制字段的读写权限，更安全、更规范
  • 作用：保护字段数据，避免外部直接修改导致的数据异常；可在读写过程中添加校验逻辑
  • 核心：
    • C#：内置 get、set 访问器，可单独设置只读（get;）、只写（set;）或读写；支持自动属性（public int Age { get; set; }），Unity 中属性无法在 Inspector 面板显示，需结合字段+属性；
    • C++：无原生属性语法，依靠 get_XXX()/set_XXX() 成员函数实现，可结合 const 修饰 get 方法保证只读；
  • 关系：通常与一个私有字段对应，隐藏字段的直接访问，对外暴露统一访问接口
  • 优势：兼顾数据安全性和访问便利性，统一数据校验入口，提升代码可读性、可维护性

函数（Method）

  • 定义：类中执行操作的函数，描述对象的行为（如人的吃饭、走路，汽车的启动、刹车）
  • 作用：实现具体的业务逻辑，操作对象的属性，完成特定功能
  • 组成：方法名、参数列表、返回值、方法体（具体执行逻辑）
  • 分类：
    • 实例方法：属于对象，需通过对象调用；
    • 静态方法：属于类，可直接通过类调用，不依赖对象；
  • 语言差异：
    • C++：包含普通成员函数、全局函数、常成员函数（const 修饰）、constexpr 函数（编译期执行）、noexcept（指定无异常）；支持函数重载、默认参数；
    • C#：方法严格依附于类，不存在独立全局函数；Unity 中常用 void Start()/void Update() 等 MonoBehaviour 生命周期方法，支持 async/await（异步方法）、params 可变参数；
  • 特点：可重复调用，减少代码冗余；支持参数传递和返回值，实现数据的交互和结果反馈
  • Unity 注意：静态方法无法访问 MonoBehaviour 实例成员，异步方法需注意主线程（Unity 中 UI/场景操作需在主线程执行）。

OOP 三大核心特性

封装（Encapsulation）

  • 核心思想：把对象的数据和操作打包隐藏，只对外暴露必要的接口，保护数据安全，降低外部依赖
  • 核心目的：隔离对象的内部实现和外部访问，避免外部操作直接修改内部数据，提高代码安全性与可维护性
  • 核心原则：隐藏不必要的实现细节，暴露必要的访问接口，遵循最小暴露原则
  • 实现方式：依托访问修饰符控制成员访问权限，私有化核心数据，对外提供标准化访问与操作接口
  • 访问修饰符：
    修饰符 作用范围 C++ C#
    private 仅当前类内部可访问 ✅ ✅
    public 所有类可访问 ✅ ✅
    protected 当前类与派生类可访问 ✅ ✅
    internal 仅当前程序集内可访问 ❌ ✅
    protected internal 程序集内 + 派生类可访问 ❌ ✅
    friend 打破权限隔离，定向访问 ✅ ❌
  • 优势：数据安全可控，减少外部非法修改；内部实现可独立迭代，不影响外部调用逻辑
  • Unity 实践：MonoBehaviour 脚本中，核心逻辑（如状态计算）私有化，对外暴露 public void Init()/public void TakeDamage() 等接口，避免外部直接修改状态字段。

继承（Inheritance）

  • 核心思想：子类复用父类的代码，并扩展独有功能，消除代码冗余，实现层级化设计
  • 核心目的：抽取通用逻辑至基类，派生类按需扩展特有能力，建立类之间的层级依赖关系
  • 相关概念：
    • 父类/基类：抽象通用能力的基础类，包含多个派生类共有属性与行为；
    • 子类/派生类：继承基类，复用非私有成员，新增自定义属性与方法；
    • 继承链：多层级嵌套继承，构建完整的业务类体系；
  • 语言规则：
    • C#：
      • 严格单类继承，支持多接口实现；
      • 所有类默认隐式继承 Object 根类，MonoBehaviour 子类继承链：Object → Component → Behaviour → MonoBehaviour；
      • Unity 中派生 MonoBehaviour 类时，父类的 Start()/Update() 需手动调用 base.Start()；
    • C++：
      • 支持单继承、多继承、虚继承（解决菱形继承问题），无统一根类；
      • 继承需显式指定继承方式（public/protected/private），默认 private 继承；
      • 支持 final 修饰方法，禁止派生类重写；
  • 关键字：
    • C#：class 子类 : 父类 { }；
    • C++：class 子类 : 继承方式 父类 { }（如 class Player : public Character { }）；
  • 优势：高代码复用性，减少重复开发；层级结构清晰，业务扩展只需新增派生类，适配迭代需求

多态（Polymorphism）

  • 核心思想：同一个接口，不同实现逻辑，基类统一约束行为规范，派生类自定义差异化实现
  • 核心目的：弱化基类与派生类的耦合关系，实现统一调用、差异化执行，提升程序扩展性
  • 核心前提：必须存在继承关系，基类定义通用行为规范，派生类重写核心行为方法
  • 跨语言实现：
    特性 C# C++
    虚方法 virtual 声明，override 重写 virtual 声明，override（C++11+）重写
    抽象类/方法 abstract class/abstract method 纯虚函数（virtual void Func() = 0;）+ 抽象基类
    接口 interface 关键字 纯虚函数抽象基类模拟
    动态绑定 运行时自动绑定 需 virtual + 指针/引用实现动态绑定
  • 核心分类：
    • 编译时多态：依托方法重载实现，程序编译阶段确定调用逻辑；
    • 运行时多态：依托方法重写与虚机制实现，程序运行阶段动态匹配子类实现；
  • 多态核心体现：基类引用/指针指向派生类对象，调用成员时自动执行派生类重写逻辑
  • 优势：符合开闭设计思想，新增业务子类无需修改原有基类代码；统一调用逻辑，简化复杂业务架构

构造函数

  • 定义：类中特殊初始化函数，与类名同名，无返回值，对象创建时自动触发执行
  • 作用：初始化对象成员数据，避免实例化后数据空值、非法值等异常状态
  • 分类：
    构造类型 C# C++
    默认构造函数 无参构造，MonoBehaviour 禁止自定义 无参构造，编译器自动生成（无自定义时）
    带参构造函数 普通类支持，MonoBehaviour 不推荐使用 支持，可重载
    静态构造函数 static 类名()（仅执行一次） static 类名()（C++ 支持）
    拷贝构造函数 无原生支持，需手动实现 ICloneable 原生支持（类名(const 类名&)）、移动构造（类名(类名&&)，C++11+）
    析构函数 终结器 ~类名()（GC 调用） ~类名()（手动/智能指针调用）
  • 继承规则：
    • C#：派生类构造函数执行前，优先调用基类构造函数；MonoBehaviour 子类无自定义构造，需通过 Awake()/Start() 初始化；
    • C++：派生类构造函数初始化列表可指定基类构造（子类(参数) : 父类(参数) {}）；
  • 特点：支持函数重载，提供多种对象初始化方式；仅在对象创建阶段自动调用
  • Unity 注意：MonoBehaviour 脚本的构造函数会被 Unity 覆盖，所有初始化逻辑需放在 Awake()/Start() 中；普通工具类（非 MonoBehaviour）可使用构造函数。

析构函数

  • 定义：类的特殊回收函数，用于对象销毁前释放资源、清理内存
  • 核心作用：平衡对象生命周期，避免内存泄漏与资源占用
  • 语言差异：
    • C++：
      • 原生支持析构函数（~类名()）、虚析构函数（virtual ~类名()，基类必须加，避免派生类资源泄漏）；
      • 需手动释放堆内存、文件句柄、网络连接等资源，推荐使用 RAII 思想（资源获取即初始化，如智能指针、std::fstream）；
    • C#：
      • 依托终结器（~类名()）与 GC 机制自动回收托管资源，终结器执行时机不确定；
      • 非托管资源（如 IntPtr 指向的原生内存）需实现 IDisposable 接口，手动调用 Dispose() 释放；
      • Unity 中 MonoBehaviour 子类可通过 OnDestroy() 回调执行销毁逻辑（如取消订阅事件、释放对象池）；

接口（Interface）

  • 定义：纯粹的行为规范与契约，仅定义方法、行为声明，不包含业务实现逻辑
  • 核心作用：突破单继承限制，定义统一行为标准，实现多维度能力扩展
  • 通用特点：无法实例化，仅可被类实现或被其他接口继承；内部成员统一为公共访问权限
  • 语言差异：
    • C#：
      • 接口完全无字段，支持默认接口方法（C# 8.0+，Unity 2021+ 支持）；
      • 接口可继承多个接口，类可实现多个接口；
      • Unity 中接口常用于解耦（如 IInteractable/IDamageable），配合 GetComponent 动态获取实现类；
    • C++：
      • 无原生接口关键字，通过「纯虚函数抽象基类」模拟（所有方法为纯虚函数，无成员变量）；
      • 支持多重继承抽象基类，实现多接口效果；
  • 与抽象类区分：
    维度 抽象类 接口
    核心定位 层级复用，包含通用实现与成员变量 行为约束，仅定义规范，无实现
    继承限制 C# 单继承，C++ 多继承 C#/C++ 均可多实现/多继承
    成员类型 可包含字段、方法、属性 仅包含方法/属性声明（C#）、纯虚函数（C++）
    Unity 场景 通用逻辑复用（如 BaseCharacter） 行为标准化（如 IDamageable）

静态成员

  • 定义：static 修饰的成员变量与成员方法，归属类本身，不属于单个实例对象
  • 特点：全局共享，所有对象共用同一份静态成员数据；无需实例化，直接通过类名访问
  • 通用约束：静态方法无法直接访问实例非静态成员，仅可操作静态数据
  • 语言差异：
    • C++：支持 static constexpr 编译期静态常量、inline static 成员变量（类内初始化）；
    • C#：静态字段在 Unity 中跨场景保留（除非手动重置），静态方法常用于工具类（如 Mathf/Time）；
  • 应用场景：
    • 全局工具能力（如 StringUtil.Trim()、MathUtil.CalculateDistance()）；
    • 全局计数器（如 GameManager.Score、EnemyManager.EnemyCount）；
    • 常量配置（如 Config.MaxPlayerHp）；
    • 共享状态管理（如 GameState.IsPaused）；

重载（Overload）

  • 定义：同一个类内部，多个方法名称一致，参数个数、参数类型、参数顺序存在差异
  • 通用规则：重载判定仅依赖参数列表，与返回值、访问修饰符无关联
  • 核心价值：同一业务行为提供多种调用形式，统一命名，提升代码易用性
  • 语言差异：
    • C++：支持函数重载、运算符重载（如 operator+）、模板重载；
    • C#：支持方法重载、索引器重载，Unity 中常用重载简化调用（如 Instantiate 多参数重载）；

重写（Override）

  • 定义：派生类对基类虚方法、纯虚方法、抽象方法进行重新实现，覆盖原有逻辑
  • 通用前提：基类方法需开启虚机制（C# virtual/abstract，C++ virtual）
  • 约束规范：
    • 重写方法需保持方法名、参数列表、返回值完全一致（协变返回值除外）；
    • C# 需显式加 override，C++11+ 推荐加 override 明确重写；
  • 概念区分：
    特性 重载（Overload） 重写（Override）
    作用范围 同一类内部 继承体系中（基类→派生类）
    判定依据 参数列表不同 方法签名完全一致，基类为虚方法
    多态类型 编译时多态 运行时多态
    关键字 无需关键字 C# override，C++ override（推荐）

抽象类

  • 定义：包含抽象方法（无实现）的类，无法直接实例化，仅作为基类被继承
  • 核心目的：抽取通用逻辑，约束派生类必须实现抽象方法，兼顾复用与规范
  • 语言差异：
    • C#：abstract class 声明抽象类，abstract 声明抽象方法（无方法体）；抽象类可包含非抽象方法；
    • C++：无 abstract 关键字，通过「包含纯虚函数的类」模拟抽象类（纯虚函数：virtual void Func() = 0;）；

SOLID 五大设计原则（C++ & Unity 落地）

单一职责原则（SRP）

  • 定义：一个类、一个方法仅负责单一业务职责，只存在一个引发修改的原因。
  • 落地实践：
    • C#：
      • 拆分 MonoBehaviour 脚本（如 PlayerMovement 仅处理移动，PlayerAttack 仅处理攻击，PlayerUI 仅处理UI）；
      • 工具类单一职责（如 FileUtil 仅处理文件读写，UIUtil 仅处理UI操作）；
    • C++：
      • 避免「万能类」（如 GameManager 不混合逻辑、UI、数据存储）；
      • 函数粒度拆分（如 CalculateDamage 仅计算伤害，不包含扣血、特效播放）；
  • 反例：一个 Player 类同时处理移动、攻击、UI更新、数据存储 → 任何一处修改都可能影响其他功能。

开闭原则（OCP）

  • 定义：软件实体应当对扩展开放，对修改关闭。
  • 落地实践：
    • C#：
      • 新增技能时，继承 BaseSkill 实现新技能类，不修改基类；
      • 新增敌人类型时，实现 IEnemy 接口，不修改敌人管理器；
      • 利用 Unity 事件系统（UnityEvent）扩展逻辑，不修改原有代码；
    • C++：
      • 新增图形类型时，继承 Shape 实现新类，不修改 CalculateTotalArea 方法；
      • 利用模板、策略模式扩展算法，不修改核心逻辑；
  • Unity 示例：新增「冰箭术」只需继承 BaseSkill，无需修改 SkillManager。

里氏替换原则（LSP）

  • 定义：所有派生类应当能够完全替代基类，且不破坏程序原有逻辑。
  • 落地实践：
    • C#：派生类不重写基类非虚方法，不弱化基类功能（如 Player 不能重写 Character 的 TakeDamage 并返回「无敌」）；
    • C++：派生类重写虚方法时，遵循「契约」（参数/返回值一致，异常行为一致）；
  • 反例：Square 继承 Rectangle 后，修改 Width 同时修改 Height → 替换基类后破坏「矩形宽高独立」的逻辑。

依赖倒置原则（DIP）

  • 定义：高层模块不依赖低层模块，二者统一依赖抽象层；抽象不依赖细节，细节依赖抽象。
  • 落地实践：
    • C#：
      • 敌人管理器依赖 IEnemy 接口，而非具体 Goblin/Orc 类；
      • 使用依赖注入（DI）给 Player 注入 IWeapon，而非直接 new Sword()；
    • C++：
      • 高层逻辑依赖 Shape 抽象类，而非具体 Circle/Rectangle 类；
      • 使用智能指针+抽象类，弱化模块耦合；

接口隔离原则（ISP）

  • 定义：使用细分的专用接口，拒绝庞大臃肿的通用接口。
  • 落地实践：
    • C#：
      • 拆分 ICharacter 为 IMovable/IAttackable/IInteractable，避免类实现不需要的方法；
      • Unity 中组件化设计（如 MovableComponent/AttackComponent）本质是接口隔离；
    • C++：
      • 拆分大抽象基类为多个小纯虚函数接口，如 IMovable/IAttackable；
  • 反例：一个 ICharacter 接口包含 Move/Attack/Interact/Save/Load → 纯UI角色被迫实现 Attack/Move 空方法。
