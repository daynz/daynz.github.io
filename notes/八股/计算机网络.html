计算机网络八股

网络基础与分层 (Network Basics & OSI/TCP/IP)

分层模型

OSI 七层模型和 TCP/IP 四层模型的区别？各层的主要协议有哪些？

  • OSI 七层: 物理层、数据链路层、网络层、传输层、会话层、表示层、应用层。理论标准，结构严谨但复杂，未完全实现。
  • TCP/IP 四层: 网络接口层（对应物理+数据链路）、网际层 (IP)、传输层 (TCP/UDP)、应用层。实际工业标准，简洁高效。
  • 五层混合模型 (教学常用): 物理层、数据链路层、网络层、传输层、应用层。
  • 协议分布:
    • 应用层: HTTP, HTTPS, DNS, DHCP, SMTP, FTP, WebSocket.
    • 传输层: TCP, UDP, SCTP.
    • 网络层: IP (IPv4/IPv6), ICMP (Ping), ARP, IGMP, OSPF, BGP.
    • 数据链路层: Ethernet, Wi-Fi (802.11), VLAN, MAC.
    • 物理层: 网线，光纤，无线电波。

数据包在发送和接收过程中，封装和解封装的过程是怎样的？

  • 发送 (封装): 数据从上往下传递。应用层数据 -> 加 TCP/UDP 头 (端口) -> 加 IP 头 (IP地址) -> 加 MAC 头 (MAC地址) -> 物理信号发送。每层将上层数据作为 payload。
  • 接收 (解封装): 信号从下往上传递。物理层还原比特流 -> 链路层检查 MAC 地址去头 -> 网络层检查 IP 地址去头 -> 传输层检查端口去头 -> 应用层获取数据。

物理与链路层

MAC 地址和 IP 地址的区别？为什么需要两者？

  • MAC 地址: 物理地址，烧录在网卡上，全球唯一（理论上），48位，扁平结构，不可变。用于局域网内设备识别。
  • IP 地址: 逻辑地址，由软件分配，32位 (IPv4) 或 128位 (IPv6)，层次化结构（网络号+主机号），可变。用于全球互联网路由寻址。
  • 原因: MAC 地址无层次，路由器无法维护全球 MAC 路由表（太大且动态变化）；IP 地址有层次，支持聚合路由，适合大规模网络互联。ARP 协议负责映射两者。

ARP 协议的工作原理？什么是 ARP 欺骗/攻击？

  • 原理: 已知目标 IP，求 MAC。
    1. 主机发送 ARP 请求广播包：“谁是 IP X？请告诉 MAC 地址。”
    2. 目标主机收到后，单播回复：“我是 IP X，我的 MAC 是 Y。”
    3. 发送方缓存该映射到 ARP 表。
  • ARP 欺骗: 攻击者伪造 ARP 响应，声称网关的 IP 对应攻击者的 MAC，导致受害者流量发给攻击者（中间人攻击）。
  • 防御: 静态 ARP 绑定、交换机端口安全、DAI (Dynamic ARP Inspection)。

VLAN 的作用是什么？如何隔离广播域？

  • 作用: 虚拟局域网，逻辑上隔离网络，提高安全性，减少广播风暴，便于管理。
  • 隔离: 交换机根据 VLAN ID 转发帧，不同 VLAN 间的通信必须通过三层设备（路由器或三层交换机）。

网络层 (Network Layer - IP)

IP 协议

IPv4 和 IPv6 的主要区别？为什么需要过渡？

  • 地址空间: IPv4 (32位，约43亿) 已耗尽；IPv6 (128位，近乎无限)。
  • 首部结构: IPv4 首部复杂（选项字段多变）；IPv6 首部固定40字节，简化处理，提高效率。
  • 配置: IPv4 需 DHCP 或手动；IPv6 支持无状态自动配置 (SLAAC)。
  • 安全性: IPv6 原生支持 IPSec。
  • 过渡技术: 双栈 (Dual Stack)、隧道技术 (6to4, Teredo)、NAT64。

子网掩码 (Subnet Mask) 和 CIDR (无分类域间路由) 的作用？

  • 子网掩码: 区分 IP 地址中的网络号和主机号。
  • CIDR: 消除传统的 A/B/C 类划分，允许任意长度的前缀（如 /24, /26）。
  • 作用:
    1. 节约地址: 按需分配，减少浪费。
    2. 路由聚合: 将多个连续小网段合并为一个大路由条目，减小路由表规模，提高查找效率。

ICMP 协议的作用？Ping 和 Traceroute 的原理？

  • ICMP: 用于报告错误和控制消息（如“目标不可达”、“超时”）。
  • Ping: 发送 ICMP Echo Request，接收 Echo Reply。测量往返时间 (RTT) 和连通性。
  • Traceroute:
    • 原理：利用 IP 包的 TTL (Time To Live) 字段。
    • 过程：发送 TTL=1 的包，第一跳路由器 TTL 减为 0 丢弃并返回 ICMP Time Exceeded；发送 TTL=2，第二跳返回… 直到到达目标。从而显示路径上的所有路由器。

路由与转发

路由表是如何生成的？静态路由和动态路由的区别？

  • 生成: 手动配置 (静态) 或 路由协议自动学习 (动态)。
  • 静态路由: 管理员手动指定下一跳。简单、安全、无带宽开销，但不适应网络拓扑变化，适合小规模网络。
  • 动态路由: 路由器之间运行协议交换信息。自适应强，适合大规模网络。
    • 内部网关协议 (IGP): RIP (距离矢量，慢，跳数限制), OSPF (链路状态，快，Dijkstra算法), IS-IS.
    • 外部网关协议 (EGP): BGP (路径矢量，用于互联网自治系统间路由)。

最长前缀匹配 (Longest Prefix Match) 原则？

  • 原则: 当路由表中有多条匹配目的 IP 的路由时，选择掩码最长（网络前缀最具体）的那一条。
  • 例子: 目的 IP 192.168.1.5，路由表有 192.168.1.0/24 和 192.168.0.0/16，优先匹配 /24。这是路由查找的核心算法。

传输层 (Transport Layer - TCP/UDP)

UDP 协议

UDP 的特点？适用场景？为什么游戏常用 UDP？

  • 特点: 无连接、不可靠、无序、面向报文、头部开销小 (8字节)、无拥塞控制。
  • 场景: 实时性要求高、容忍少量丢包的场景。如：视频直播、语音通话 (VoIP)、DNS 查询、在线游戏。
  • 游戏原因:
    1. 低延迟: 无需三次握手，无需重传等待，头部小。
    2. 队头阻塞避免: TCP 重传会阻塞后续数据包，导致游戏卡顿；UDP 丢包可直接跳过或用最新状态覆盖。
    3. 可控性: 游戏引擎可在应用层实现自定义的可靠机制（如只重传关键指令）或拥塞控制。

TCP 协议

TCP 的三大特性？（连接管理、可靠传输、流量/拥塞控制）

  1. 连接管理: 面向连接，通过三次握手建立，四次挥手断开。
  2. 可靠传输: 序列号、确认应答 (ACK)、超时重传、校验和、去重、排序。
  3. 流量与拥塞控制: 滑动窗口、慢启动、拥塞避免、快重传、快恢复。

TCP 三次握手 (Three-Way Handshake) 的过程？为什么是三次而不是两次？

  • 过程:
    1. Client -> Server: SYN=1, seq=x (请求建立)。
    2. Server -> Client: SYN=1, ACK=1, seq=y, ack=x+1 (同意并确认)。
    3. Client -> Server: ACK=1, seq=x+1, ack=y+1 (确认)。
  • 为什么三次:
    • 防止已失效的连接请求突然传到服务器，导致服务器错误开启资源。
    • 双方确认彼此的发送和接收能力正常（两次只能确认一方的发送和另一方的接收）。
    • 同步初始序列号 (ISN)。

TCP 四次挥手 (Four-Way Wave) 的过程？为什么是四次？TIME_WAIT 状态的作用？

  • 过程:
    1. Client -> Server: FIN=1 (我要关了)。
    2. Server -> Client: ACK=1 (知道了，但我可能还有数据要发)。
    3. Server -> Client: FIN=1 (我也发完了，我要关了)。
    4. Client -> Server: ACK=1 (好的，再见)。
  • 为什么四次: TCP 是全双工的。一方发送 FIN 仅代表“我数据发完了”，不代表“我不能接收了”。所以 Server 的 ACK 和 FIN 通常分开发送（除非 Server 也没数据了，可合并为三次，但标准是四次）。
  • TIME_WAIT:
    • 位置: 主动关闭方（通常是 Client）。
    • 时长: 2MSL (Maximum Segment Lifetime)。
    • 作用:
      1. 确保最后的 ACK 能到达 Server（若丢失，Server 重传 FIN，Client 需在 TIME_WAIT 中响应）。
      2. 让本连接持续时间内产生的所有旧报文段在网络中消失，避免干扰新连接（相同四元组）。

TCP 如何保证可靠性？（序列号、ACK、重传机制）

  • 序列号 (Seq): 给每个字节编号，解决乱序和去重。
  • 确认应答 (ACK): 累计确认，告知对方期望收到的下一个序号。
  • 超时重传 (RTO): 发送后未收到 ACK，超时后重传。RTO 动态计算。
  • 快速重传 (Fast Retransmit): 收到 3 个重复 ACK，立即重传丢失包，无需等待超时。
  • 选择性确认 (SACK): 告知对方哪些块收到了，只重传丢失的块。

TCP 流量控制 vs 拥塞控制？滑动窗口机制？

  • 流量控制 (Flow Control): 端到端，防止发送方太快把接收方缓冲区撑爆。基于接收窗口 (rwnd)。
  • 拥塞控制 (Congestion Control): 全局，防止过多数据注入网络导致链路/路由器过载。基于拥塞窗口 (cwnd)。
  • 发送窗口: Min(rwnd, cwnd)。
  • 拥塞控制算法:
    1. 慢启动: cwnd 指数增长，直到阈值 (ssthresh)。
    2. 拥塞避免: cwnd 线性增长 (加法增大)。
    3. 快重传/快恢复: 遇到丢包（3 重复 ACK），cwnd 减半，进入快恢复，而非重新慢启动。

什么是 TCP 粘包/拆包？如何解决？

  • 现象: TCP 是流协议，无消息边界。
    • 粘包: 发送方发了两个小包，接收方一次读到了合并的大包。
    • 拆包: 发送方发了一个大包，接收方分多次读到。
  • 原因: Nagle 算法（合并小包）、接收缓冲区大小限制。
  • 解决 (应用层协议设计):
    1. 定长消息: 固定长度。
    2. 分隔符: 如 \n, \r\n (HTTP, FTP)。
    3. 长度字段: 消息头包含 Content-Length (最常用，如 Protobuf, 游戏私有协议)。

应用层 (Application Layer)

HTTP 协议

HTTP 1.0, 1.1, 2.0, 3.0 (QUIC) 的区别？

  • HTTP 1.0: 短连接，每次请求都要 TCP 三次握手。
  • HTTP 1.1: 长连接 (Keep-Alive)，复用 TCP 连接；引入管道化（但有队头阻塞）；断点续传。
  • HTTP 2.0: 多路复用 (二进制分帧，解决队头阻塞)；头部压缩 (HPACK)；服务器推送。基于 TCP。
  • HTTP 3.0 (QUIC): 基于 UDP。解决 TCP 层面的队头阻塞（丢包只影响当前流）；0-RTT 握手（更快）；连接迁移（IP 变了不用重连，适合移动网络）。

GET 和 POST 的区别？

  • 语义: GET 获取资源（幂等，安全）；POST 提交数据（非幂等，可能改变服务器状态）。
  • 参数位置: GET 在 URL 中；POST 在 Body 中。
  • 限制: GET 受 URL 长度限制，不安全（日志可见）；POST 无长度限制，相对安全。
  • 缓存: GET 可被浏览器缓存；POST 默认不缓存。

HTTP 状态码含义？(200, 301/302, 400/401/403/404, 500/502/503/504)

  • 2xx: 成功 (200 OK, 204 No Content).
  • 3xx: 重定向 (301 永久, 302 临时, 304 未修改/缓存命中).
  • 4xx: 客户端错误 (400 坏请求, 401 未授权, 403 禁止访问, 404 未找到).
  • 5xx: 服务器错误 (500 内部错误, 502 坏网关, 503 服务不可用, 504 网关超时).

DNS 与 CDN

DNS 解析过程？递归查询和迭代查询的区别？

  • 过程: 浏览器缓存 -> 系统缓存/hosts -> 本地 DNS 服务器 (LDNS) -> 根域名服务器 -> 顶级域名服务器 (.com) -> 权威域名服务器 -> 返回 IP。
  • 递归: 客户端向 LDNS 发起，LDNS 必须给出最终结果（LDNS 替客户端跑腿）。
  • 迭代: LDNS 向根/顶级/权威查询，服务器只返回“下一步去哪查”，LDNS 自己一步步查。

CDN (内容分发网络) 的原理？如何加速游戏资源下载？

  • 原理: 将资源缓存到全球各地的边缘节点。用户请求时，通过 DNS 调度到最近/最快的节点。
  • 加速:
    1. 就近访问: 减少物理距离和网络跳数。
    2. 负载均衡: 分散源站压力。
    3. 协议优化: 边缘节点通常支持 HTTP/2, QUIC 等高速协议。
    4. 游戏应用: 更新包、贴图、模型、热更脚本的分发。

WebSocket

WebSocket 与 HTTP 的区别？握手过程？

  • 区别: HTTP 是请求 - 响应模式，短效；WebSocket 是全双工长连接，服务器可主动推送数据。
  • 握手: 基于 HTTP 升级。
    1. Client 发送 Upgrade: websocket 请求。
    2. Server 回复 101 Switching Protocols。
    3. 之后建立 TCP 长连接，传输 WebSocket 帧。
  • 游戏应用: 实时对战、聊天室、状态同步。

五、网络安全 (Network Security)

加密与认证

HTTPS 的工作原理？SSL/TLS 握手过程？

  • 原理: HTTP + SSL/TLS。结合对称加密（传输数据）和非对称加密（交换密钥）。
  • 握手简述:
    1. Client Hello (支持算法列表，随机数)。
    2. Server Hello (选定算法，证书，随机数)。
    3. Client 验证证书，生成预主密钥 (用 Server 公钥加密)。
    4. Server 用私钥解密，双方根据随机数和预主密钥生成相同的会话密钥 (对称)。
    5. 后续通信使用会话密钥加密。
  • 优势: 机密性、完整性、身份认证。

对称加密与非对称加密的区别？常见算法？

  • 对称加密: 加解密用同一密钥。速度快，适合大数据量。密钥分发困难。算法：AES, DES, RC4.
  • 非对称加密: 公钥加密，私钥解密（或私钥签名，公钥验签）。速度慢，适合密钥交换和签名。算法：RSA, ECC, DH.

常见攻击

DDoS 攻击 (分布式拒绝服务) 的类型及防御？

  • 类型:
    • 流量型: UDP Flood, ICMP Flood (打满带宽)。
    • 连接型: SYN Flood (耗尽连接表)。
    • 应用层: HTTP Flood (CC 攻击，模拟正常请求耗尽 CPU/DB)。
  • 防御:
    • 高防 IP / 清洗中心 (过滤异常流量)。
    • CDN 分散流量。
    • 限流、熔断、验证码。
    • SYN Cookie (防御 SYN Flood)。

XSS (跨站脚本) 和 CSRF (跨站请求伪造) 的区别及防御？

  • XSS: 攻击者注入恶意脚本到网页，用户在浏览时执行，窃取 Cookie。
    • 防御: 输入过滤，输出转义，CSP (内容安全策略)。
  • CSRF: 诱导已登录用户点击链接，冒充用户发送请求（如转账）。
    • 防御: Token 验证 (Anti-CSRF Token)，检查 Referer/Origin，SameSite Cookie 属性。

中间人攻击 (MITM) 如何防范？

  • 原理: 攻击者拦截并篡改通信。
  • 防范: 使用 HTTPS (证书链验证)，HSTS (强制 HTTPS)，公钥指纹绑定 (Certificate Pinning，游戏客户端常用)。

六、游戏开发特定场景 (Game Dev Specifics)

网络架构

C/S (Client/Server) 和 P2P (Peer-to-Peer) 架构的区别？游戏如何选择？

  • C/S:
    • 特点: 所有逻辑在服务器，客户端只表现。防作弊强，状态一致性好。
    • 缺点: 服务器成本高，单点故障风险，延迟受服务器位置影响。
    • 适用: MMORPG, FPS, MOBA (竞技类)。
  • P2P:
    • 特点: 节点互通，无中心服务器（或仅做信令）。延迟低（直连），成本低。
    • 缺点: 极易作弊， NAT 穿透困难，主机退出影响大，状态难同步。
    • 适用: 小型联机 (2-4人)，格斗游戏，早期主机游戏。
  • 混合: 帧同步 (Lockstep) 常配合 P2P 或轻量服务器；状态同步必用 C/S。

帧同步 (Lockstep) 与 状态同步 (State Synchronization) 的区别？

  • 帧同步:
    • 原理: 服务器只转发操作指令，所有客户端逻辑完全一致，本地演算。
    • 优点: 流量极小，服务器压力小，易于实现回放。
    • 缺点: 对确定性要求极高 (浮点数问题)，外挂难防 (本地可改逻辑)，掉线重连复杂。
    • 适用: RTS, MOBA (王者荣耀), 格斗。
  • 状态同步:
    • 原理: 服务器计算所有逻辑，定期广播实体状态 (坐标、血量) 给客户端。
    • 优点: 安全性高，客户端容错好，逻辑简单。
    • 缺点: 流量大，服务器负载高，延迟感知明显（需预测和插值）。
    • 适用: MMORPG, FPS (部分), 卡牌。

弱网优化手段有哪些？（预测、插值、冗余、压缩）

  • 延迟补偿:
    • 客户端预测 (Client-side Prediction): 本地先执行操作，服务器确认后修正。
    • 服务器回滚 (Lag Compensation): 服务器根据客户端上报的时间戳，回溯状态进行判定 (FPS 常用)。
  • 平滑处理:
    • 死算 (Dead Reckoning): 根据速度和方向推算位置。
    • 插值 (Interpolation): 渲染时在其他玩家的状态点之间平滑过渡。
  • 协议优化:
    • 二进制协议: Protobuf, FlatBuffers (比 JSON 小且快)。
    • 差分更新: 只发送变化的数据 (AOI, 兴趣范围)。
    • 冗余发送: 关键包多发几次 (UDP 可靠层)。
    • 压缩: Zstd, LZ4 压缩 Payload。

NAT 穿透技术 (STUN, TURN, ICE) 的原理？

  • 背景: 内网设备无公网 IP，无法直接连接。
  • STUN: 客户端询问 STUN 服务器“我的公网 IP:Port 是多少？”，尝试打洞直连。失败率高（对称型 NAT）。
  • TURN: 中继服务器。若直连失败，所有流量经 TURN 转发。稳定但成本高（带宽）。
  • ICE: 综合策略。收集所有候选地址 (Host, STUN, TURN)，按优先级尝试连接，选最佳路径。WebRTC 和游戏联机标配。
