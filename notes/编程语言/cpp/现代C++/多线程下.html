条件变量

在 <condition_variable> 头文件中提供了条件变量（Condition Variable） 机制，核心用于解决多线程间的 “生产者-消费者” 同步问题 —— 让一个 / 多个线程等待某个条件满足，当条件成立时，由其他线程通知等待的线程继续执行。这是比单纯使用互斥锁更高效的同步方式（避免线程无意义的轮询等待）。

背景

互斥锁的局限性：仅用互斥锁实现 “等待条件” 时，线程需不断加锁检查条件（轮询），导致 CPU 资源浪费。

条件变量的核心价值：让等待线程进入休眠状态，直到被通知唤醒，彻底避免轮询的 CPU 浪费。

核心概念与基础语法

核心组件

类型 核心特性
std::condition_variable 仅支持配合std::unique_lock<std::mutex>使用，功能更全（推荐）
std::condition_variable_any 支持配合任意锁类型（如std::lock_guard、自定义锁），但有轻微性能开销

核心函数

函数 功能
wait(unique_lock<mutex>& lck) 释放锁并阻塞线程，直到被通知唤醒；唤醒后重新加锁，检查条件（需外层循环）
wait(unique_lock<mutex>& lck, Predicate pred) 重载版：唤醒后仅当pred()为 true 时才继续，否则重新休眠
notify_one() 唤醒一个等待的线程（随机选择）
notify_all() 唤醒所有等待的线程
wait_for(lck, 时长, pred) 等待指定时长，超时或条件满足时返回（返回值为 bool：条件是否满足）
wait_until(lck, 时间点, pred) 等待到指定时间点，超时或条件满足时返回

核心使用场景

生产者-消费者模型

经典的单生产者 - 单消费者模型：生产者生产数据后通知消费者，消费者等待数据就绪。

  • 虚假唤醒：等待的线程可能在没有被notify的情况下被唤醒（操作系统底层机制导致）

  • 解决方案：必须用循环检查条件（wait的重载版自带循环，或手动写 while 循环）

使用例

多消费者唤醒（notify_all ()）

多个线程等待同一条件，条件满足时唤醒所有等待线程

超时等待（wait_for）

避免线程永久等待，设置超时时间，超时后主动退出。

核心规则与注意事项

  1. 必须配合std::unique_lock

    • std::condition_variable::wait() 会在休眠前释放锁，唤醒后重新加锁，只有std::unique_lock支持手动解锁 / 加锁（std::lock_guard不支持），因此必须使用unique_lock。

  2. 条件变量的 “条件” 必须受互斥锁保护

    • 读取 / 修改条件（如data_ready）时，必须加锁，避免数据竞争；

    • 通知线程需先修改条件，再调用notify（顺序不可颠倒）。

  3. 避免 “丢失通知”

    • 错误示例：通知线程先调用notify，再修改条件，可能导致等待线程错过通知；

    • 正确做法：先加锁修改条件，再调用notify（如场景 1 的生产者线程）。

  4. notify_one() vs notify_all()

    • notify_one()：唤醒一个等待线程（适合单消费者场景），开销小；

    • notify_all()：唤醒所有等待线程（适合多消费者场景），开销大，需确保所有线程都需要被唤醒。

异步操作

在 <future> 头文件中引入了异步操作机制，核心用于实现异步执行任务 + 同步获取结果 的编程模式——让任务在后台线程执行，主线程可继续处理其他逻辑，待需要结果时再获取（或等待任务完成）。这是比直接使用 std::thread 更便捷的并发编程方式，无需手动管理线程和同步（如互斥锁 / 条件变量）。

异步操作的核心价值：标准化封装 “任务执行 + 结果获取 + 同步”，无需手动编写同步代码，大幅简化并发编程。

背景

直接使用线程的痛点：用 std::thread 实现 “后台执行任务并获取结果” 时，需手动处理同步（如互斥锁 + 条件变量），代码冗余且易出错。

核心组件与基础概念

C++11 异步操作的核心组件分为三类，协同实现 “异步任务 - 结果获取”

组件 核心作用
std::future<T> 未来值：获取异步任务的结果（T 为结果类型，void 表示无返回值），仅可被一个线程获取一次
std::shared_future<T> 共享未来值：可被多个线程多次获取结果
std::promise<T> 承诺：与future配对，用于主动设置任务结果 / 异常
std::packaged_task<T> 任务包装器：封装可调用对象（函数 / Lambda），将其与future绑定
std::async() 异步函数：最便捷的异步操作入口，直接启动异步任务并返回future（推荐首选）

std::async

std::async 是最简单的异步操作入口，自动创建线程执行任务，并返回future用于获取结果。

策略说明：

  • std::launch::async：强制创建新线程，立即执行任务；
  • std::launch::deferred：延迟执行（懒加载），仅当调用future.get()/wait()时才在当前线程执行；
  • 默认策略：std::launch::async | std::launch::deferred。

异步计算求和

std::promise / std::future

promise 用于主动设置任务结果（或异常），与future配对使用，适用于 “手动控制任务完成时机” 的场景（如多线程协作）。

线程间传递结果

std::shared_future

std::future 仅能被一个线程获取一次结果，shared_future 可被多个线程多次获取，适用于 “多线程共享同一任务结果” 的场景。

多线程读取结果

核心成员函数

std::future / std::shared_future

函数 功能
get() 阻塞获取结果（future仅可调用一次，shared_future可多次调用）
wait() 阻塞等待任务完成（不获取结果）
wait_for(时长) 超时等待：返回future_status（ready/timeout/deferred）
wait_until(时间点) 等待到指定时间点，返回future_status
valid() 判断future是否有效（未调用get()且关联的任务存在）

std::promise

函数 功能
get_future() 获取与该 promise 绑定的 future 对象（只能调用一次）
set_value(T) 设置结果值，唤醒等待的 future；未设置则析构时抛异常
set_exception(exception_ptr) 设置异常，让 future.get() 时抛出该异常
swap(promise& other) 交换两个 promise 的内部状态

超时等待任务

std::packaged_task

packaged_task 封装可调用对象（函数 / Lambda），将其执行结果绑定到future，适用于 “任务需复用 / 延迟执行” 的场景。

封装并执行任务

核心成员函数

函数 功能
get_future() 获取绑定的 future，仅调用一次
operator() 执行任务，调用内部函数，将结果存入共享状态
make_ready_at_thread_exit() 执行任务，但延迟到线程退出时才让 future 就绪
valid() 判断 packaged_task 是否拥有有效任务 / 状态
reset() 重置共享状态，可重新执行任务（保留原可调用对象）
swap(packaged_task& other) 交换两个 packaged_task 的内部状态

处理异步任务的异常

异步任务抛出的异常会被存储到future中，调用get()时重新抛出

线程本地存储

引入了标准化的线程本地存储机制（核心关键字 thread_local），允许创建 “每个线程独有一份” 的变量实例——不同线程访问该变量时，操作的是各自独立的副本，而非共享的全局 / 静态变量。这是解决多线程数据共享冲突的轻量化方案，无需加锁即可保证线程安全。

线程本地存储的核心价值：为每个线程分配独立的变量副本，线程对变量的操作仅作用于自身副本，彻底避免数据竞争，且无需互斥锁 / 原子操作。

背景

全局 / 静态变量的线程安全问题：普通全局 / 静态变量是进程级共享的，多线程同时读写会引发数据竞争

核心语法

thread_local 是 C++11 新增的存储类说明符（与static/extern同级），可修饰全局变量、静态变量、类的静态成员变量。

修饰位置 变量生命周期 初始化时机
全局变量 线程创建时初始化，线程退出时销毁 线程首次访问时（懒初始化）
函数内静态变量 线程创建时初始化，线程退出时销毁 线程首次调用该函数时
类的静态成员变量 线程创建时初始化，线程退出时销毁 线程首次访问该成员时

修饰全局变量

修饰函数内静态变量

修饰类的静态成员变量

关键规则

  • 不可修饰局部非静态变量：thread_local 仅能修饰全局、静态（函数内 / 类成员）变量，修饰普通局部变量会编译报错；

    • void wrong_func() {
    thread_local int x = 0; // 错误：局部非静态变量不能用thread_local
}

避免线程安全的函数重入问题

某些函数依赖全局状态（如随机数生成器），多线程调用时会出错，TLS 可让每个线程有独立的状态副本

性能优化（替代锁 / 原子操作）

对于高频访问的线程私有变量，TLS 无需加锁 / 原子操作，性能远高于共享变量 + 同步

TLS vs 其他线程安全方案

方案 核心特性 性能 适用场景
thread_local 每个线程独立副本，无数据竞争 极高 线程私有状态、高频访问的线程独有关变量
std::mutex 互斥访问共享变量 低 复杂临界区、多线程共享数据
std::atomic 硬件级原子操作，无锁 高 简单共享变量（计数器、标志位）
函数参数传递 线程私有，无共享 中 少量、低频传递的线程私有数据

选型建议

  1. 线程私有状态：优先用thread_local（最简洁、性能最优）；
  2. 简单共享计数器：用std::atomic；
  3. 复杂共享临界区：用std::mutex；
  4. 少量临时数据：用函数参数传递。

标准库容器的线程安全性

  • 规则明确：
    1. 读写冲突：如果多个线程同时访问同一个容器实例，且其中至少有一个是写操作（插入、删除、修改元素），必须使用互斥锁 (std::mutex) 进行保护。
    2. 纯读并发：如果多个线程同时对同一个容器实例进行只读访问（没有写操作），则是安全的，不需要加锁。
    3. 不同元素访问：C++11 标准保证，如果多个线程访问不同的容器实例，或者访问同一个容器中完全不同的元素（且不改变容器结构，如 size/capacity），通常是安全的（具体取决于容器类型，std::vector 修改不同元素通常安全，但 std::list 节点操作需小心）。
